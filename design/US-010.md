# US-010 · Behaviour library in the runtime

## Approach

A new module, `runtime/src/behaviour.rs`, with one file per behaviour under
`runtime/src/behaviour/`. Like `data` and `physics`, it has no dependencies and no
`agb`, so every behaviour is tested on the host.

**The shared shape.** Each behaviour is a plain `Copy` struct of the settings it
needs, plus any state it keeps. It has the same two functions:

```rust
impl Patrol {
    /// The settings from the entity's properties, or None if it has none of them.
    pub fn from_entity(entity: &Entity) -> Option<Self>;
    /// One frame. Moves the actor and says what happened.
    pub fn update(&mut self, actor: &mut Actor, world: &World, cx: &Context) -> Event;
}
```

A `Behaviour` trait with those two functions lets US-013's generated dispatch call
them all the same way. There are no trait objects and nothing is boxed.

- **`Actor`** is the entity while it is live: its feet in world pixels, where it was
  placed (`home`), its velocity, which way it faces, its hitbox (an offset and a size
  from the feet, which the game takes from the sprite sheet), and whether it is still
  alive. Entities in the ROM do not change, so this is the "entity" that the
  criterion's update function takes. `Actor::placed(world, room, number, hitbox)`
  builds one from a placed entity.
- **`Context`** holds the player's `Body`, the clock, the buttons, and the
  abilities the player has. `Buttons` is a plain bit set (A, B, the D-pad and so on),
  so the runtime stays free of `agb`. The game fills it from agb's input once a
  frame.
- **`Event`** is what came of the frame: `None`, `Hurt`, `Collect { value }`,
  `Grant { ability }`, `Checkpoint { x, y }`, `Fire(Shot)`, `Spawn { x, y }`,
  `Opened`. The game decides what an event does: play a sound, add to the score,
  respawn the player. The library never changes game state it does not own.
- **`Pool<T, N>`** is a fixed array for things made while the game runs, such as
  shots and spawned enemies. Adding to a full pool fails, and nothing is allocated.
- **`Abilities`** is a 32-bit set. An ability is a number from 0 to 31, set in a
  property.

**The behaviours.** The property names below become the declarations in US-011.

| Behaviour | Reads | Does |
| --- | --- | --- |
| `Patrol` | `patrol` (reach, px), `patrol_pace` (frames per px, default 2) | Walks back and forth around `home`, worked out from the clock as the sample does now. The debug map's note that patrols follow the frame count stays true. |
| `Collectible` | `value` | When the player touches it: `Collect { value }`, and the actor dies. |
| `Hazard` | (none) | When the player touches it: `Hurt`. Joined with `Patrol`, it makes the sentry bot. |
| `Projectile` | made by `Shooter` | Moves at its speed. Dies on a solid cell or when its time runs out. Touching the player: `Hurt`. |
| `Shooter` | `fire_every` (frames), `shot_speed` (px a frame), `sight` (px) | Every `fire_every` frames, if the player is within `sight`, `Fire(Shot)` towards the player along x. The game puts the shot in a `Pool<Projectile, N>`. |
| `MovingPlatform` | `travel_x`, `travel_y` (px), `travel_pace` (frames per px) | Goes back and forth between `home` and `home` + travel, driven by the clock. `carry(actor, body, before)` lands a falling body on its top edge and moves it along with the platform. |
| `Door` | `needs_ability` (−1 means none) | Closed until the player touches it while holding the ability (with no ability: while pressing Up). Then `Opened`, once. While closed, `block(actor, body, before)` stops the body going through. |
| `Checkpoint` | (none) | The first touch: `Checkpoint { x, y }`, where the player will come back to. |
| `AbilityPickup` | `grants_ability` | When the player touches it: `Grant { ability }`, and the actor dies. |
| `Spawner` | `spawn_every` (frames), `max_alive` | Every `spawn_every` frames, while fewer than `max_alive` of its children are alive, `Spawn { x, y }`. The game tells it when a child dies. |

**The sample.** The sentry bot becomes `Patrol` and `Hazard`, and coins and diamonds
become `Collectible`. `patrol()`, `SENTRY_PACE` and the overlap code go from
`main.rs`. The rule "a type with `value` is a collectible" stays, now as
`Collectible::from_entity`. The game builds the behaviour structs from the entity
each frame. That costs what the property lookups cost today, and it needs no
live-entity table: that table comes with US-013.

Alternatives considered:
- *One `enum Behaviour` with every kind.* Simpler to dispatch, but a game crate could
  not add its own kinds (US-018).
- *Doors and platforms as collision cells added to the world.* Cells are aligned to
  the 8-pixel grid, so a platform between two cells would jitter. Pushing the body
  out against a box is exact.
- *Behaviours that change game state themselves (score, `Collected`).* They would
  then hold `&mut` borrows of the game. Returning events keeps them testable and
  keeps the decisions in the game.

## Format changes

None. Behaviours read the properties an entity type already defines. Declaring them
to the studio is US-011.

## Hardware cost

- **ROM:** only the behaviours a game calls are linked. Estimated at 1 to 3 KB for
  all of them.
- **IWRAM and EWRAM:** none for the library. Each struct is 4 to 16 bytes, and a
  `Pool<Projectile, 8>` is about 200 bytes, on the game's side.
- **CPU:** the sample's frame work, measured with `--features measure`. The target
  was no more than 2 % worse in the worst frame.

**Measured for US-010a** (2026-11-21). Release builds of `HEAD` and of the change,
run headless with the same inputs: 100 frames idle, then walk right and jump, which
takes three coins and passes the sentry. Figures are hundreds of CPU cycles; a
frame has 2808.

| | Before | After |
| --- | --- | --- |
| Worst frame | 709 | 721 (+1.7 %) |
| Average frame | 296 | 312 (+5.4 %, 0.6 % of a frame) |
| Release `.text` | 65,484 B | 76,072 B |
| Dev ROM | 310,080 B | 311,148 B |
| IWRAM, EWRAM | 2,504 B, 464 B | unchanged |

- **Worst frame:** within the target.
- **Average:** over it. The cost is looking properties up by name on every entity in
  view, every frame. A first version looked up `patrol` on every entity and was at
  +7 %, so the sample now gives behaviours by type, as it did before. The new
  `patrol_pace` lookup is about 300 cycles of what is left. Reading properties once,
  not every frame, belongs with US-011 and US-013, which give each entity type its
  behaviours and a live table.
- **Where the average goes** (measured after, same inputs): the old `main.rs` built
  against the new runtime gives 709 and 297, so the runtime change itself costs
  nothing. Reading the buttons costs nothing measurable (721 and 312 without it).
  The patrol done without `from_entity` gives 713 and 304. With no property lookups
  at all (each type's settings hardcoded, for the measurement only) it is 705 and
  289: faster than before US-010a, because the old loop also looked up `value` every
  frame. All of the extra cost is looking properties up by name.
- **`.text`:** the 10 KB is not library code. LLVM now inlines more physics and
  camera code into the sample's `main` (`camera_target` twice, `floor_under`,
  `slide_around`, `Cells::class`); `main` went from 17 KB to 30 KB. The `measure`
  build, which is laid out differently, grew by 16 bytes.

## Tests

- **Criterion 1** (each behaviour has host tests): `runtime/src/behaviour/tests.rs`,
  at least two cases for each behaviour, on worlds built with `data::write`:
  - patrol: turning points and facing
  - collectible: taken once
  - hazard: overlap and near miss
  - projectile: stops at a wall and when its time runs out
  - shooter: rate and range
  - platform: carries a standing body, and a body jumps up through it
  - door: blocks while closed, opens with and without an ability
  - checkpoint: fires once
  - pickup: grants its ability
  - spawner: stops at `max_alive` and spawns again after a child dies
  - pool: full and reuse
- **Criterion 2** (plain struct and update signature): the `Behaviour` trait,
  implemented by all nine behaviours. A compile test calls every one of them through
  one generic function.
- **Criterion 3** (the sample uses the library, `main.rs` shorter):
  `cd sample && cargo build`. Then the sample is run headless with `run_rom`: the
  sentry walks and hurts, and a coin is taken and counted. Compared against pictures
  taken before the change, and `wc -l sample/src/main.rs` against 374 lines.

## Decisions

- **Split** (author, 2026-11-21) into two branches:
  - **US-010a:** the shared shape (`Actor`, `Context`, `Buttons`, `Event`, the
    `Behaviour` trait), with patrol, collectible and hazard, and the sample moved
    onto them.
  - **US-010b:** projectile and shooter, moving platform, door, checkpoint, ability
    pickup, spawner, `Pool` and `Abilities`.

  The sample's criterion goes with US-010a, because that part has the behaviours
  the sample uses. The shape is then proven in a real game before the other six are
  built on it.
- **Door with no ability** (author): it opens on a touch while pressing Up.
- **Property names** (author): each behaviour's own names start with its own word,
  so that two behaviours on one type cannot clash (a shooter and a spawner would
  both have had `every`). `patrol` and `value` stay as they are, because the
  sample's project and authors' rooms already use them.

## Built as, US-010b

Where the code differs from the table above:

- **`Projectile` keeps its own speed.** It does not take it from the actor, so a
  projectile placed in a room with `shot_speed` flies too. `Shot::launch(hitbox)`
  gives the actor and the projectile together, ready for a `Pool`. A shot starts at
  the shooter's middle, so shot sprites are best anchored in their middle.
- **`Shooter` sight** is a square: within `sight` pixels both across and up and
  down. While the player is in sight, the shooter turns to face them. Defaults:
  `shot_speed` 2, `sight` 96.
- **A closed door** counts as touched when the player stands right against it.
  Otherwise its own blocking would keep the player from ever touching it.
- **`Door`, `Checkpoint` and `Spawner` keep state** (open, reached, children
  alive). The game keeps their structs between frames, unlike `Patrol`, `Hazard`
  and `Collectible`, which can be rebuilt every frame.
- **`Spawner`'s `max_alive`** is 3 if not set. `Projectile::DEFAULT_LIFE` is 240
  frames.
- **Tests:** 20 more in `runtime/src/behaviour/tests.rs`, 77 in the runtime in all.
  Each behaviour was broken on purpose once (wall check, aim, carry, one-way, open
  once, open stops blocking, reached once, pickup taken, spawn count, pool slot),
  and a test failed each time. The first try at the one-way case passed while
  broken, so `a_body_can_jump_off_a_platform` was added.
