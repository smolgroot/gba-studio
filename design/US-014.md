# US-014 · Prefabs with per-instance overrides

## Approach

An entity type already works as a prefab for its **behaviour** properties, since
US-012: a placed entity stores a value only when it differs from the type's
(`behaviourOverride`, `shownBehaviourValue` in `core/src/behaviours.ts`), the panel
marks it and has a reset button (`BehaviourOverrides`), and typing the type's value
back drops it. Codegen and the data section writer already give an entity the
type's value when it stores none. What is left is the type's own **properties**
(`EntityType.props`, the "property definitions"), and the writers that bypass the
panel:

1. **Own properties in the panel.** `Selected entity` shows a type's own property
   as the type's default until the entity sets its own, marks a set one (the same
   `Field marked` as for behaviours) and gives it a reset button. Setting a value
   equal to the default drops it.
2. **One rule, in core.** A new `core/src/prefab.ts` holds what both kinds of
   property share, so the panel and the tools cannot disagree:
   - `shownEntityValue(type, entityProps, name)` → `{ value, inherited, overridden }`
     for an own property (its default is the type's value), and for a behaviour
     property it calls the existing `shownBehaviourValue`.
   - `entityOverride(type, entityProps, name, value)` → the props with the value set,
     or removed when it is `undefined` or equals what the type gives.
   - `redundantProps(type, entityProps)` → the names whose values equal what the type
     gives, and `overriddenProps(type, entityProps)` → the props without them. A name the type does not have is kept: the
     validator already warns about it, and dropping it would hide the mistake.
3. **Tools store only overrides.** `entity_add` and `entity_update` pass the
   entity's props through `overriddenProps` before they save, and say so in their
   answer when they dropped any ("Dropped 2 values that Sentry bot already has:
   patrol, value."). Their descriptions say that props are the values that differ
   from the type's.
4. **Existing rooms.** A room file that stores values equal to the type's is still
   read and built as before. It is cleaned only when the entity's props are next
   written by the panel or a tool. The studio does not rewrite author files in
   bulk.

"Changing the type's default updates every copy that kept it" needs no new code: a
copy that stores nothing is given the type's value by codegen and by the section
writer, so a changed default reaches it on the next build or patch (and live, by
US-003). It is shown by a test.

Alternatives considered:
- *A Problems warning for a stored value equal to the type's.* It would flag every
  entity in a project made before this story, which is noise for no fault; the
  clean-on-write rule does the same job.
- *Clean every room when it is saved.* It rewrites files the author did not touch.
- *Store a "kept" marker for a value that equals the default on purpose.* A format
  change for a case the author can solve by giving the type that value.

## Format changes

None. `Entity.props` already holds overrides only by convention; nothing in
`schema.ts`, `model.rs` or `FORMAT_VERSION` changes, and no old project fails to
load. `docs/reference/project-format.md` already says what a missing property
means: it gets one sentence on the rule.

## Hardware cost

None. The ROM gets the same values as before: a value equal to the type's and a
missing one build to the same bytes.

## Tests

- *Room files store only overridden properties:*
  - `core/test/prefab.test.ts`: `entityOverride` drops a value equal to the type's
    own default and to a behaviour's inherited value (the type's, else the
    behaviour's default); keeps one that differs; `overriddenProps` drops the equal
    ones of both kinds, keeps the others, and keeps a name the type does not have.
  - `server/test/behaviours.test.ts` (MCP, as the other entity tool tests there):
    `entity_add` and `entity_update` with a value equal to the type's save an
    entity whose props are `{}`, say what they dropped, and keep a different one.
  - A byte-for-byte check: the section written for a room with the redundant value
    equals the one written without it (`core/test/` datasection test).
- *Properties marks overridden values and has "reset to type default":*
  - Behaviour properties: done in US-012 (`entity-overrides` screenshot,
    `core/test/behaviouredit.test.ts`).
  - Own properties: `core/test/prefab.test.ts` for `shownEntityValue` (`overridden`,
    `inherited`) and for reset (`entityOverride(..., undefined)`); the
    `entity-overrides-own` screenshot (a type with a property, an entity that sets
    it, marked, with its reset button).
- *Changing the type's default updates every copy that kept it* (the story's
  summary line): a test writes the section for two entities of one type, one
  storing a value and one not, changes the type's default, and reads the values back
  from the section: the one that stored nothing follows, the other keeps its own.

## Decided

- No Problems line for a stored value equal to the type's: the rule is applied when
  props are written, and old rooms are left as they are.

## Open questions

None.
