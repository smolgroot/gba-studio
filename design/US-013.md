# US-013 · Generated entity dispatch, no hand-written match

## Approach

Today the sample walks every entity of every room in view each frame. For each one
it reads the entity record from ROM, builds a fresh `Actor`, and asks for `Patrol`,
`Collectible` and `Hazard` by name in code (`from_entity`, three times). Adding a
behaviour to the sample means adding a fourth `if let`. Reading the settings again
every frame is why the frame is 301, not 296 (`design/US-011.md`).

This story adds a **live entity table**. Each live entity keeps its actor and its
behaviours, already built from the ROM settings. One call updates them all.

**1. The runtime: one type for "any behaviour", and a table of entities**
(`runtime/src/behaviour/live.rs`, new)

- `enum Attached { Patrol(Patrol), Collectible(Collectible), … }` has one variant for
  each of the ten behaviours.
  - `Attached::from_settings(number, &Settings) -> Option<Attached>` matches on the
    behaviour number.
  - `Attached::update` forwards to the behaviour.
  - This is the only `match`, and it is over behaviours, not entity types. A test
    checks that it covers every number in `DECLARATIONS`.
- `LiveEntity` holds an `Actor`, the type (`kind`), the room, its index in the world,
  and `behaviours: [Option<Attached>; MAX_BEHAVIOURS]` in the type's order. It holds
  no reference into the data section, so once it is built nothing in it reads ROM.
- `LiveEntities<const N: usize>` has **one slot per entity of the world**, by
  `World::entity_index`.
  - A slot is built from the ROM the first time its room becomes active, and then
    kept. Leaving a room and coming back finds its entities as they were left: a
    door still open, a spawner's count, a taken coin (the author's answer to open
    question 3).
  - `enter(&World, room, hitbox_of, skip)` makes the room and the rooms that touch
    it on the world map (corners included) the active ones, at most
    `MAX_ACTIVE_ROOMS` (16). It builds the slots of those rooms that aren't built
    yet. `skip` lets the game leave out what it has collected.
  - `update(&World, &Context, before, event)` is the frame loop over the active
    rooms' living entities. For each one:
    - `before(entity)`, the game's hook, answers `Dispatch::Behaviours` or
      `Dispatch::Handled`;
    - unless the answer is `Handled`, its behaviours run in the type's order;
    - every event that isn't `Event::None` goes to `event(entity, event)`.
  - `active()` and `active_mut()` give the living entities of the active rooms, for
    drawing and for what the game does itself. `get(index)` gives any built one.
  - `clear()` forgets everything. The sample calls it after a live apply that
    changes entities, because their indices may have moved.
  - Entities past `N`, or behaviours past `MAX_BEHAVIOURS` (both only possible on a
    ROM patched past what the studio allows), aren't made, and are counted
    (`dropped()`).

**2. Codegen: `include_data!()` gives the typed entry points** (`codegen/src/lib.rs`)

- `data::HITBOXES: [Hitbox; kinds]`: each type's hitbox from its sprite, as
  `SpriteSheet::hitbox` gives it, or an empty box for a type with no sprite. These are
  now in `data`, so the table doesn't need `include_gfx!`.
- `data::LIVE_ENTITIES`: the table's size, `live::slots_for(entities in the
  project)`. That's the count plus a quarter, at least 16 more, rounded up to 16, so
  entities placed during play (live apply) still fit.
- `data::Entities` is `LiveEntities<LIVE_ENTITIES>`. `data::entities()` gives the
  game the one table, a `static`. agb puts statics in EWRAM, not on the IWRAM stack.
  A second call panics.
- `data::enter_room(&mut Entities, &World, room, skip)` calls `enter` with `HITBOXES`.
- `data::update_entities(&mut Entities, &World, &Context, before, event)` calls
  `update`, with `before` and `event` given the entity's `EntityKind` as well:
  `|kind, e| if kind == EntityKind::PlayerStart { Dispatch::Handled } else { Dispatch::Behaviours }`.

The dispatch can't be a per-type `match` written by codegen. Live apply can give a
type a behaviour without a build, so code can't fix each type's list. Codegen writes
the typed wrapper, the size and the hitboxes. The runtime dispatches on the
behaviour numbers in the section.

**3. The sample** (`sample/src/main.rs`)

- It calls `enter_room` at the start and when the hero enters another room. After a
  live apply it calls `clear`, then `enter_room`.
- Its entity loop becomes a single `data::update_entities(…)`:
  - The `before` hook handles `PlayerStart`.
  - The `event` hook turns `Collect` into score and a sound: the diamond sound for
    `EntityKind::Diamond`, the coin sound otherwise. It turns `Hurt` into a respawn.
- Drawing walks `entities.active()`, culls by camera, and shows the type's sprite.
- `main.rs` names no `Patrol`, `Collectible` or `Hazard`.
- Entities are active in the hero's room and the rooms touching it. Rooms sit on a
  grid of screens, so these are the only rooms the camera can show.

Alternatives considered:
- *Codegen writes a `match EntityKind` per type.* It's stale after a live apply that
  adds a behaviour, which is the case the section exists for.
- *A trait object per behaviour (`&mut dyn Behaviour`).* Each entity would need
  storage of no fixed size, or a pool for each behaviour, and `Behaviour` isn't
  object-safe (`from_settings`, a const).
- *Size the table by `ENTITY_SLOTS`, the most entities the section could hold.* For
  the sample that's 1239 slots, about 130 KB of EWRAM, nearly all unused. The
  project's count plus room to grow is enough, and the studio says when a live
  apply goes past it.
- *Keep only the active rooms' entities, built again on each room change.* It's
  smaller, but a room's state is lost when the hero leaves it (the author chose to
  keep it).
- *Cache settings only, and keep rebuilding actors from ROM each frame.* It still
  reads every entity record each frame, and it gives later behaviours
  (projectile, platform, spawner) no state that lasts between frames.

## Format changes

- **`project.json`:** no change, and `FORMAT_VERSION` stays the same. There's one
  new rule: **an entity type has at most 4 behaviours** (`MAX_BEHAVIOURS`, exported
  to the studio in `core/src/behaviourschema.ts`). It's a problem in the studio and in
  the build, in the same words: "entity type "many" has 5 behaviours; an entity can
  have at most 4". `codegen/fixture/bad-behaviours/` gets a type with 5.
  - The most any type can have is 9, and no project has more than 2.
  - The limit goes in `docs/reference/limits.md` and the README.
- **Data section:** the manifest (what the compiled game holds) ends with one more
  `u32`: the size of the generated entity table (`LIVE_ENTITIES`).
  - A manifest without it, written by an older build, reads as "not known", so the
    section stays at version 1.
  - The TypeScript writer copies it from the ROM's manifest, as it does the rest.
  - `needsBuild` adds a reason when a live apply would put more entities in the world
    than that: "the game has room for 32 entities; the project now has 33".
  - The change goes in `layout.rs`, `write.rs`, `core/src/datasection.ts` and
    `docs/reference/data-section.md`, and the shared fixture `studio_data.bin` is
    regenerated.

## Hardware cost

- **RAM (EWRAM):** a slot is 108 bytes (measured by `a_live_entity_is_small`): `Actor` 36, ids 6, and 4 ×
  `Option<Attached>` at 16 (the largest behaviours are 12 bytes plus a tag). A host
  test pins the size with `size_of`.
  - The sample has 15 entities, so 32 slots, 3,532 bytes with the table's own fields.
  - A world of 500 entities gets 640 slots, about 69 KB of the 256 KB. That goes in
    `docs/reference/limits.md`.
- **ROM:** about 8 bytes per entity type for `HITBOXES`, 4 for the manifest word, and
  the dispatch code, measured from the ELF before and after.
- **CPU:** settings and positions are read from ROM once per entity. Each frame, an
  entity costs its behaviours' `update` calls and an enum match.
  - The target is the criterion: an average of 296 or less, with `--features
    measure` on the US-010 run (100 frames idle, then walk right and jump).
  - US-011b measured 289 with settings hardcoded, which is roughly the floor here.
- **Sprites:** unchanged.

## Tests

- **Criterion 1** (`include_data!()` gives an `update_entities` that calls each
  entity's behaviours):
  - Runtime host tests in `runtime/src/behaviour/tests.rs`, on a world from the
    writer:
    - a sentry type with `patrol, hazard` moves on the clock, and the hazard reports
      `Hurt` where the patrol moved it (order kept);
    - a collectible reports `Collect` once, then is dead;
    - every behaviour number in `DECLARATIONS` builds an `Attached`.
  - Codegen test (`codegen/src/lib.rs` tests): the generated `studio_data.rs`
    declares `update_entities`, `load_entities`, `Entities`, `LIVE_SLOTS` and
    `HITBOXES`, and `LIVE_SLOTS` is the value the fixture project gives.
  - `cd sample && cargo build` compiles it, and `main.rs` has no `Patrol`,
    `Collectible` or `Hazard` (a check in the same codegen test, reading
    `sample/src/main.rs`).
- **Criterion 2** (a game can handle a kind before or instead of the generated code):
  - Host tests:
    - `Dispatch::Handled` for a kind runs none of its behaviours;
    - `Dispatch::Behaviours` after changing the actor in `before` runs them on the
      changed actor;
    - `event` gets each event with the entity's kind.
  - The sample uses both hooks (`PlayerStart`, the diamond sound).
- **Criterion 3** (settings read once and kept, frame no slower than 296):
  - A host test loads the table from a world, then runs `update` against another
    world with the same rooms but different settings: the entities keep the first
    world's settings. `LiveEntities` has no lifetime, so it can't hold a reference
    into either.
  - A host test leaves a room and comes back: an entity's state is as it was.
  - Manifest: both writers give the regenerated fixture byte for byte, a section
    without the word reads as "not known", and a vitest test gets the needs-build
    reason past the size.
  - The 4-behaviour problem: `codegen/fixture/bad-behaviours/` gets a type with
    5 behaviours, and its `expected.txt` a line. `reports_bad_behaviour_settings`
    and `server/test/behaviourrules.test.ts` check it.
  - Measured: release with `--features measure`, the US-010 run, average 296 or
    less, recorded here under "Built as".
  - The sample's headless pictures are identical to the US-010 baseline (`run_rom`,
    same inputs), and walking into the sentry still sends the hero back.
  - `scripts/check-new-enemy.ts` (US-012) still passes.

## Decisions

- **Rooms left keep their state** (author, 2026-11-22): the table has a slot for
  every entity of the world, kept once built, rather than only the active rooms'.
- **At most 4 behaviours per type**, and **active means the hero's room and the
  rooms touching it**: as proposed. The author went ahead without changing them.

## Built as

- **Only the rooms in view run.** Every frame, `update` takes an area (the camera's
  screen; the generated `data::view(camera)`), and runs only the active rooms that
  overlap it. `visible(area)` gives what to draw the same way.
  - Running every active room's entities, the shaft's included while the hero is in
    the entry, made the average 327 against 320 on a longer run. The old loop also
    only looked at rooms in view.
  - Entities of a touching room off screen are kept, but they wait. That's what the
    old loop did, and patrols and platforms follow the clock anyway. Waking by
    distance is still US-064.
- **Where the table lives.** The table is a plain `static`, so agb puts it in EWRAM
  (3,532 bytes for the sample's 32 slots, copied from ROM at start-up). In IWRAM it
  measured the same, so it stays out of the scarce IWRAM.
- **The sample draws room by room**, and asks `view.shows(room)` once per room
  rather than once per entity. That was worth 4 hundred cycles on average.

**Frame time** (release, `--features measure`, hundreds of cycles, worst and
average). The US-010 run is 100 frames idle, 40 walking right, 20 walking right and
jumping, and 40 walking right. It wasn't written down before. These inputs give the
US-011b build 715 and 302, against the 716 and 301 recorded for it.

| Build | Worst | Average |
| --- | --- | --- |
| Before US-010a (recorded) | 709 | 296 |
| US-011b (`HEAD`), this run | 715 | 302 |
| Table, every active room updated and drawn | 708 | 296 |
| The same, drawing checks `view.shows` once per entity, rooms in view only | 708 | 296 |
| **Kept: rooms in view, `view.shows` once per room** | **702** | **287** |

**The same pictures:** the release ROM run headless with the inputs above, and on a
longer run (100 idle, then walking and jumping right through three coins, past the
sentry and into the next room). Every picture is byte-for-byte the same as `HEAD`'s.

**Size** (release ELF): `.text` went from 67,292 to 81,228 bytes. Most of the growth
is the dispatch, which LLVM inlines into `main`. `.ewram` went from 464 to 4,252
bytes: the table is 3,532 of them, and the 256 bytes of active room bounds are part
of the rest. `.iwram` is the same, at 2,504. The release ROM went from 240,076 to
259,488 bytes.
