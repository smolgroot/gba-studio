# US-013 · Generated entity dispatch, no hand-written match

## Approach

Today the sample walks every entity of every room in view each frame. For each one
it reads the entity record from ROM, builds a fresh `Actor`, and asks for `Patrol`,
`Collectible` and `Hazard` by name in code (`from_entity`, three times). Adding a
behaviour to the sample means adding a fourth `if let`. Reading the settings again
every frame is why the frame is 301, not 296 (`design/US-011.md`).

This story adds a **live entity table**. Each live entity keeps its actor and its
behaviours, already built from the ROM settings. One call updates them all.

**1. The runtime: one type for "any behaviour"** (`runtime/src/behaviour/live.rs`, new)

- `enum Attached { Patrol(Patrol), Collectible(Collectible), … }` has one variant for
  each of the ten behaviours.
  - `Attached::from_settings(number, &Settings) -> Option<Attached>` matches on the
    behaviour number.
  - `Attached::update(&mut self, &mut Actor, &World, &Context) -> Event` forwards to
    the behaviour.
  - This is the only `match`, and it is over behaviours, not entity types. Adding a
    behaviour to the runtime adds a variant here, next to `DECLARATIONS`. A test
    checks that the two list the same numbers.
- `LiveEntity` holds:
  - `actor: Actor`
  - `kind: u16`
  - `index: u16`: the entity's index in the world, as `World::entity_index` gives it
    and as `Collected` takes it.
  - `behaviours: [Option<Attached>; MAX_BEHAVIOURS]`: in the type's order, built
    once.
  - It holds no reference into the data section, so nothing in it reads ROM after
    it is made.
- `LiveEntities<const N: usize>` is a fixed array of up to `N` live entities. It never
  allocates.
  - `load(&mut self, &World, rooms, hitbox_of, skip)` fills the table from those
    rooms' entities. `skip` lets the game leave out what it has already collected.
    `load` reads settings from ROM, once.
  - `update(&mut self, &World, &Context, before, event)` is the frame loop. For each
    live entity:
    - call `before(entity)`, the game's hook, which answers `Dispatch::Behaviours`
      or `Dispatch::Handled`;
    - unless the answer is `Handled`, run its behaviours in the type's order;
    - pass every event that isn't `Event::None` to `event(entity, event)`.
  - `iter()` and `iter_mut()` are for drawing, and for whatever the game does itself.
  - `dropped()` is how many entities didn't fit at the last `load` (see Hardware cost).
- `World::rooms_touching(room)` gives a room and the rooms that touch it on the world
  map, corners included. It's worked out from origins and sizes when it's called,
  which happens on a room change, not every frame.

**2. Codegen: `include_data!()` gives the typed entry points** (`codegen/src/lib.rs`)

- `data::HITBOXES: [Hitbox; kinds]` holds each type's hitbox from its sprite, or none.
  These are now in `data`, so `update_entities` doesn't need `include_gfx!`.
- `data::LIVE_SLOTS` is the table's size, worked out from the project: the most
  entities in any room plus the rooms touching it, rounded up to 8, and at least 16.
- `data::Entities` is `LiveEntities<LIVE_SLOTS>`.
- `data::load_entities(&mut Entities, &World, room, skip)` loads `room` and the
  rooms that touch it, with `HITBOXES`.
- `data::update_entities(&mut Entities, &World, &Context, before, event)` calls
  `LiveEntities::update`, with `before` and `event` given an `EntityKind` as well as
  the live entity. That way a game handles a kind by name:
  `|kind, e| if kind == EntityKind::PlayerStart { Dispatch::Handled } else { Dispatch::Behaviours }`.

The dispatch can't be a per-type `match` written by codegen. Live apply (US-011's
reason for the `S_BEHAVIOURS` section) can give a type a behaviour without a build,
so the code can't fix each type's list. Codegen writes the typed wrapper, the
capacity and the hitboxes. The runtime dispatches on the behaviour numbers in the
section.

**3. The sample** (`sample/src/main.rs`)

- It loads the table at the start, when the hero enters another room, and after a
  live apply that changes entities. A reload resets the live state. Patrols follow
  the clock, so they don't jump.
- Its entity loop becomes a single `data::update_entities(…)`:
  - The `before` hook handles `PlayerStart` (nothing to draw or run).
  - The `event` hook turns `Collect` into score and a sound: the diamond sound for
    `EntityKind::Diamond`, the coin sound otherwise. It turns `Hurt` into a respawn.
- Drawing walks `entities.iter()`, culls by camera, and shows the type's sprite.
- No `Patrol`, `Collectible` or `Hazard` appears in `main.rs`.
- What's on screen doesn't change. One thing does: entities are live in the hero's
  room and the rooms touching it, where before they were live in every room in
  view. At 240x160, the camera only ever sees rooms that touch the hero's room.

Alternatives considered:
- *Codegen writes a `match EntityKind` per type.* It's stale after a live apply that
  adds a behaviour, which is the case the section exists for.
- *A trait object per behaviour (`&mut dyn Behaviour`).* Each entity would need
  storage of no fixed size, or a pool for each behaviour, and `Behaviour` isn't
  object-safe (`from_settings`, a const).
- *Keep one live entity for every entity in the world (`ENTITY_SLOTS`).* That's 1239
  slots, about 130 KB, mostly unused. Rooms near the hero are what's on screen, and
  US-064 refines this later (waking by distance).
- *Cache settings only, and keep rebuilding actors from ROM each frame.* It still
  reads every entity record each frame, and it gives later behaviours
  (projectile, platform, spawner) no state that lasts between frames.

## Format changes

- There are no changes to `project.json` or the data section, and `FORMAT_VERSION`
  stays the same.
- There is one new rule: **an entity type has at most `MAX_BEHAVIOURS` (4)
  behaviours.** It's a problem in validation (`core/src/validate.ts`) and in codegen,
  with the same words: "entity type "sentry-bot" has 5 behaviours; an entity can
  have at most 4". Both check it against the shared fixture
  `codegen/fixture/bad-behaviours/`.
  - The most any type can have today is 9 (ten, less one of `shooter` or
    `projectile`), and no project has more than 2.
  - The limit goes in `docs/reference/limits.md` and the README.
- On a ROM that was live-patched past the limit, `load` keeps the first 4 behaviours
  and counts the rest in `dropped()`. The studio's check stops this before it
  happens.

## Hardware cost

- **RAM:** a `LiveEntity` is an estimated 104 bytes: `Actor` 36, ids 4, and 4 ×
  `Option<Attached>` at 16 (the largest behaviours, `MovingPlatform` and `Shooter`,
  are 12 bytes plus a tag). A host test pins the size with `size_of`.
  - In the sample, a room plus the rooms touching it has 15 entities, so `LIVE_SLOTS`
    is 16, or about 1.7 KB.
  - The table is a local in `main`, which agb puts on the IWRAM stack. If the size
    test or a project shows it is too large for that, the generated `Entities` goes
    in a `static` in EWRAM instead. I'll measure this on the sample build.
- **ROM:** about 4 bytes per entity type for `HITBOXES`, plus the dispatch code
  (estimated under 2 KB, measured from the ELF before and after).
- **CPU:** settings are read once per `load`. Each frame, an entity costs its
  behaviours' `update` calls and an enum match, with no ROM reads of entity records.
  - The target is the criterion: an average of 296 or less, with `--features measure`
    on the US-010 run (100 frames idle, then walk right and jump).
  - US-011b measured 289 with settings hardcoded, which is roughly the floor here.
- **Sprites:** unchanged.

## Tests

- **Criterion 1** (`include_data!()` gives an `update_entities` that calls each
  entity's behaviours):
  - Runtime host tests in `runtime/src/behaviour/tests.rs`, on a world from the
    writer:
    - a sentry type with `patrol, hazard` moves on the clock, and the hazard reports
      `Hurt` where the patrol moved it (order kept);
    - a collectible reports `Collect` once, then is dead;
    - every behaviour number in `DECLARATIONS` builds an `Attached`.
  - Codegen test (`codegen/src/lib.rs` tests): the generated `studio_data.rs`
    declares `update_entities`, `load_entities`, `Entities`, `LIVE_SLOTS` and
    `HITBOXES`, and `LIVE_SLOTS` is the value the fixture project gives.
  - `cd sample && cargo build` compiles it, and `main.rs` has no `Patrol`,
    `Collectible` or `Hazard` (a check in the same codegen test, reading
    `sample/src/main.rs`).
- **Criterion 2** (a game can handle a kind before or instead of the generated code):
  - Host tests:
    - `Dispatch::Handled` for a kind runs none of its behaviours;
    - `Dispatch::Behaviours` after changing the actor in `before` runs them on the
      changed actor;
    - `event` gets each event with the entity's kind.
  - The sample uses both hooks (`PlayerStart`, the diamond sound).
- **Criterion 3** (settings read once and kept, frame no slower than 296):
  - A host test loads the table from a world in a `Vec`, drops the `Vec`, and runs
    `update` against another world with the same rooms. That compiles and passes
    only if the table holds no reference into the first world.
  - The new 4-behaviour problem: `codegen/fixture/bad-behaviours/` gets a type with
    5 behaviours, and its `expected.txt` a line. `reports_bad_behaviour_settings`
    and `server/test/behaviourrules.test.ts` check it.
  - Measured: release with `--features measure`, the US-010 run, average 296 or
    less, recorded here under "Built as".
  - The sample's headless pictures are identical to the US-010 baseline (`run_rom`,
    same inputs), and walking into the sentry still sends the hero back.
  - `scripts/check-new-enemy.ts` (US-012) still passes.

## Open questions

1. **At most 4 behaviours per entity type**, as a new problem. Is 4 right? The
   alternative is a capacity codegen works out from the project, which live apply
   could then go past.
2. **Entities live in the hero's room and the rooms touching it**, not in "every
   room in view". At the GBA's screen size these are the same set. Is that fine
   before US-064 adds waking by distance?
3. **When the live table is reset.** A reload on a room change resets each entity's
   state, though not what was collected. That's invisible today (patrols follow the
   clock). For a door opened or a spawner's count it would matter later. Should the
   state of the rooms just left be kept, or is that later work (a new story)?
