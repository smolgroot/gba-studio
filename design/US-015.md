# US-015 · Edit collision classes in the interface

## Approach

**Project settings → Collision classes** becomes a table in a new
`app/src/panels/collision.tsx` (`panels.tsx` is 760 lines and gains nothing but one
line). A row per class: colour, name, id, kind, the floor heights when the kind is
slope, and a bin. **Add collision class** adds one at the end, as **Add entity type**
does. Every edit is a `commit('project', …)`, so it is one undo step on the project,
as the entity types are.

What a class is made of, and what stands on it, decides what the interface may do:

- **Colour, name, kind, slope heights** are only the class's own. Changing the kind to
  slope gives heights 0 and 8 (a 45 degree rise); changing it away drops them, as the
  schema requires. Heights are whole numbers from 0 to 8.
- **The id** is how tilesets name a class (`tileset.collision`), and it becomes a
  constant in the game's code (`data::class::SOLID`: codegen's `constant`, which also
  makes two ids that differ only by `-` or `_` the same name). Renaming one changes
  the tilesets that name it, and game Rust that names the constant. The id field says
  so, and refuses an id that is not valid (lowercase letters, digits, `-`, `_`), is
  taken, or has the same name in code as another.
- **The order** is data. A room's painted collision stores a class's *position* plus
  one, and the game numbers classes by position, so a class can be added at the end
  but not moved, and deleting one in the middle moves the ones after it. There is no
  move button, and the page says why.
- **The first class** is the one a tile with no class of its own has. It cannot be
  deleted; its kind and colour can be changed.

**Deleting a class that is used.** `core/src/collision.ts` (new) has:

- `classUsage(docs, id)` → the tilesets that give a tile this class (with how many
  tiles) and the rooms with cells of it, painted or from a tile (with how many cells),
  computed as the room editor and the data section do.
- `withoutClass(docs, id)` → the project without the class, the tilesets without the
  tiles that named it (a tile with none falls back to the first class), and the rooms
  with their painted collision repointed: cells painted with this class go back to
  following their tile (0), and cells painted with a class after it count one less.
  It returns only the documents that changed.
- `renameClass(docs, from, to)` → the project and the tilesets that name it.

The bin asks before deleting a class that is used: a dialog lists the tilesets and
rooms from `classUsage` ("Placeholder tiles: 3 tiles; Entry: 52 cells") and says what
will happen to them. A class nothing uses is deleted at once (and can be undone).

**Undo across documents.** Deleting a used class and renaming an id each change
several documents, and today an undo step is one document's. The store gets
`commitGroup(owner, others)`: the owner (the project) goes into history as now, and
the others' earlier versions are kept with that history entry (a `WeakMap` from the
owner's previous document, in a small pure module `app/src/groupundo.ts` so it is
tested like `doctabs.ts`). Undo and redo on the project restore the others with it.
They do so only if each is still as the group left it; if one was edited since, the
undo does nothing and Project settings says "Not undone: Entry was changed after the
class was deleted. Undo that change first." A class's other edits stay single-document.

Not in this story: moving a class, and MCP tools for classes (`write_document` on the
project already can change them, and answers with problems). The room editor's
selected class (an index) is kept in range when classes are deleted.

Alternatives considered:
- *Refuse to delete a used class.* Safe, but the story says to ask, and it leaves the
  author hunting for every use by hand.
- *Delete it and leave the uses.* Painted collision would silently point at other
  classes, and tiles would name a class that is not there.
- *Store painted collision by id.* A format change for every room, for what a
  confirmation and a remap do.

## Format changes

None. The schema, `model.rs` and `FORMAT_VERSION` do not change. Adding, deleting or
renaming a class changes the list of classes the game is built with, so Patch says
"needs a build", as `needsBuild` already does for a change to the class ids or their
order. A new kind or slope height is written into the data section, so it is patched in
without a build, and a name or colour is not in the ROM at all.

## Hardware cost

None. The game gets the same kinds of data. The class list is at most 255 classes
(codegen's limit): **Add collision class** stops there and says so.

## Tests

- *Every field in the collision class schema can be edited, with undo:*
  - `core/test/collision.test.ts`: `classFieldProblem` accepts and refuses ids (invalid
    characters, taken, same name in code); kind changes give and drop slope heights; a
    class written by the editor parses with `CollisionClass`.
  - `core/test/collision.test.ts`: `renameClass` changes the project and the tilesets
    that name the id and nothing else.
  - `app/test/groupundo.test.ts`: a group is undone and redone with its owner, restores
    the others only if unchanged since, and is refused (with its reason) if not.
  - The `collision-classes` screenshot (a table with a slope class and a used class
    being deleted) and, for undo, the page's Undo button.
- *Deleting a class in use asks first and says which tilesets and rooms use it:*
  - `core/test/collision.test.ts`: `classUsage` lists tilesets and rooms with counts,
    for tile-derived and painted cells; an unused class has no uses.
  - `core/test/collision.test.ts`: `withoutClass` repoints painted cells (to 0 for the
    deleted class, down one after it) and drops the tiles' entries, and a data section
    written before and after gives every other cell the same class id. It refuses the
    first class and the last class.
  - The `collision-delete` screenshot shows the question with its list.

## Decided

- A used class is deleted after the question, and what used it is repointed as above.
- The id is editable, carried to the tilesets, with a warning about game code.
- Undo across documents is grouped under the project, and refused with its reason when
  a touched document has changed since.
