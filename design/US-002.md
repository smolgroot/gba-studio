# US-002 · Patch level data into a built ROM without compiling

## Approach

A patch writes a new data section (US-001) over the old one inside the built `.gba`
file. It touches no other byte. The Play panel already restarts the game when the
ROM file changes, so a patch is: compute the section, check that it fits, write the
file, and tell the clients.

**Computing the section: a TypeScript port in `core`.** `core/src/datasection.ts`
turns the project documents into section bytes, using the layout in
`runtime/src/data/layout.rs`. Most of the inputs already exist in TypeScript:
`rleDecode`, `effectiveCollision` (moved from `server/src/render.ts` into `core`),
entity defaults and the physics schema. The port and codegen are kept in step by a
shared-fixture test, as `AGENTS.md` asks for code computed in both languages:
`cargo test` writes the fixture project's section to
`codegen/fixture/expected/studio_data.bin`, and vitest checks that the TypeScript
port produces the same bytes. The fixture now has a property of every type
(integer, boolean, text with a non-ASCII character, enum) and a room with music. A
second check runs on `sample/`: patching the built ROM with the unchanged project
leaves it byte-identical. `core` has no Node or DOM types, so the port carries its
own UTF-8 encoder and decoder, and the fixture test lives in `server/test`.

Alternatives considered:
- *Codegen compiled to wasm.* One implementation, but it needs a wasm toolchain in
  the studio build, and the PNG reading and file access would have to be cut out of
  codegen.
- *Codegen as a native binary called by the server.* This needs cargo on the
  machine at patch time, and the desktop app would have to ship a binary for each
  platform.

**Knowing what the ROM was compiled with: a manifest part in the section.** A patch
is only valid if everything the game compiled from the project is unchanged:
- the names that become code (`EntityKind`, `class::*`, `room::*`);
- the tilesets and their tile counts;
- the background pictures, with their tile and palette costs;
- the audio tracks.

Codegen adds an eighth part to the section, `manifest`, which lists these. US-001's
readers skip parts they don't know, so the layout stays version 1. Before
patching, `core` compares the manifest in the ROM with the current project. Any
difference refuses the patch with a reason in the project's terms, for example
"entity type \"bat\" is new: build the game", or "room \"cave\" was added". US-004
will show these reasons in the top bar.

The manifest also stores each picture's tile and palette cost. With those, the
patch runs codegen's VRAM checks (1024 tiles, 16 palettes, 4 layers) without
decoding a picture. Painting more distinct tiles can therefore still fail
correctly, with codegen's own message.

**Making "byte for byte" hold: no counts in the generated code.** The generated code
must not depend on anything a patch can change. Today `data::ENTITY_COUNT` does, so
adding a coin would change the code. I propose replacing it with
`data::ENTITY_SLOTS`, the number of entities the section's capacity could hold
(`capacity / 12`). The game sizes `Collected` from that, so a patched ROM with more
entities can still remember every one of them. That removes US-001's open question
about extra entities.

**What a patch checks before writing:**
1. The ROM's section is found, and its version is 1.
2. Every document loaded (valid JSON and schema). The studio's other checks are
   stricter than a build in places: the sample's `world.json` places a room
   "kitchen" that has no file, which a build ignores. So a patch takes what a build
   takes. `writeSection` makes codegen's data checks, in codegen's words: layer
   sizes, tile numbers within the tileset, unknown tilesets, entity types and
   tracks, the start room, and the VRAM budgets from the manifest.
3. The manifest matches.
4. The new section is no larger than the ROM's capacity. If it is larger, the patch
   refuses with "the level data is now N bytes; this build has room for M. Build
   the game.", and the Play panel shows a **Build dev** button.

The patch writes the new section, padded with zeros to the old capacity. The
capacity field keeps the ROM's value. A section identical to the one in the ROM is
not written, so the game does not restart. The file is written beside the ROM and
renamed over it, so the Play panel never reads half a file.

**Where it runs:**
- **Server:** `server/src/patch.ts` holds `patchRom(project, mode)`. It returns
  `patched` (with the bytes used and the capacity) or `needs-build` (with reasons).
  After a patch it broadcasts the new build status, so the ROM's modification time
  changes and the Play panel's auto-restart reloads the game.
- **Automatic:** the Play panel gets **Patch on change**, on by default. While a game
  is running, each document change, debounced by 150 ms, calls `POST /api/patch`.
  A refusal shows as a line in the panel, with a **Build dev** button.
- **CLI:** `pecten-studio patch <folder> [--release] [--json]` exits with 0 when it
  patched or the ROM was already up to date, 3 when a build is needed, and 1 when
  the project has errors. Code 2 already means a usage error.
- **MCP:** `patch_rom { release?: boolean }` answers like the CLI, with the
  project's problems.

Only the dev ROM is patched by default. A release build is for sharing, so it is
patched only on request.

## Format changes

- **Section part 7, `manifest`** (codegen and runtime layout, documented in
  `docs/reference/data-section.md`): the ids of entity types, collision classes and
  rooms in order; each tileset's id, tile count and palette count; each picture's
  path, tile count and palette count; track ids. These are stored as strings and
  counts. The full layout is in the build step. It is a few hundred bytes for the
  sample.
- **Generated code:** `ENTITY_COUNT` is replaced by `ENTITY_SLOTS`. This is a
  breaking change for games: the sample, the scaffold and the docs change with it.
- No project format change and no `FORMAT_VERSION` bump.

## Hardware cost

- **ROM:** the sample's section uses 10,700 bytes, up from 10,468. The manifest adds
  232 bytes.
- **RAM:** `ENTITY_SLOTS` is 1,233 for the sample's 14,796-byte capacity, so
  `Collected` is 39 words (156 bytes) instead of 1. It is a local in `main`, on the
  stack in IWRAM.
- **CPU:** none at run time.

## Time from an edit to the game

Measured on a copy of the sample through a real server. The chain is the one the
Play panel runs: save a room over the API, wait for the server's change message
(120 ms gather), wait the panel's 150 ms debounce, `POST /api/patch`, wait for
`rom-patched`, fetch the ROM, and boot the emulator to the first game picture.
Five rounds took 609, 472, 460, 497 and 461 ms; the patch itself took 20 to 58 ms.
The headless run steps the emulator as fast as it can. In the panel, the game's
boot frames play in real time, which adds about 150 ms. The story's target is 2 s.

## Open questions

Answered by the author: test byte-for-byte at the same capacity; use
`ENTITY_SLOTS`; a TypeScript port; **Patch on change** on by default.

Still open:
- Changed art pixels and Rust code are not detected: a patch says the ROM is up to
  date when only a PNG or `src/` changed. That is US-004.
- The Play panel's new line has no automated test. The app has no component tests,
  and Playwright is not installed (US-108).

Previously:

1. **What "byte for byte" means.** A full build sets the capacity to the data used
   plus the reserve, so it differs whenever the data size changes. So "the same
   ROM as a full build" can only hold for a full build with the same capacity. I
   propose testing it that way, as in the table above: same section, same capacity,
   and the rest of the ROM identical.
2. **`ENTITY_SLOTS` instead of `ENTITY_COUNT`.** This costs about 150 bytes of IWRAM
   in the sample. In return, adding or removing entities never needs a build. The
   alternative is to keep `ENTITY_COUNT` and refuse a patch that changes the entity
   count, but then adding a coin needs a build.
3. **A TypeScript port** rather than wasm or a native binary, kept in step by a
   shared byte fixture.
4. **Patch on change**, on by default while the game runs.
