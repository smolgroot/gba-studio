# US-108 · Scripted documentation screenshots

## Approach

`scripts/screenshots.ts` starts the studio's server, opens each listed route in
headless Chromium (Playwright), runs the shot's actions and saves a PNG.

**A copy of the project, not the project itself.** The shots that were left manual
needed the project changed: a patch, a change that needs a build, a real build.
The script now serves a copy in a temporary folder, removed at the end. It is made
again after any shot that edits or clicks **Build…**, **Patch** or **Create…**, so
shots don't see each other's changes. Three details make the copy behave like the
project:
- File times are kept. The studio compares them with the ROM's to say whether it
  is up to date (US-004), and fresh times would make everything look changed.
- `target/` is linked, so a build only recompiles the game crate (8 s for the
  sample).
- Path dependencies one level up (`../runtime`, `../codegen`) are linked beside
  the copy. A copy next to the project would land in the repository's Cargo
  workspace, which refuses to build it.

**New actions:** `within` for a click whose name appears twice (the Play panel's
**Play** and the activity bar's), `fill`, `select`, `edit` (append to a file or
set JSON paths, as an author or agent would), and `waitForText`. `waitForText`
is case-sensitive, because a plain match took "patched into" for "Patched in".
`fill` leaves the field, because the studio's fields commit on blur.

**Seeing failures:** a failed shot saves `<name>.failed.png`. `--out <dir>` writes
the pictures somewhere else, to look before replacing the published ones.

Alternatives considered:
- *Serve the project and undo changes afterwards with git.* This depends on the
  project being a clean git checkout, and a build or patch still touches `dist/`.
- *Fake the states (mock API answers).* Then the pictures would not show what the
  studio really does.

## Format changes

None. `docs/screenshots.json` gains action kinds; old entries are unchanged.

## Hardware cost

None.

## Tests

| Criterion | Check |
| --- | --- |
| Playwright in the lockfile, runs on a clean checkout | `playwright` in root `devDependencies` and `pnpm-lock.yaml`. In a fresh `git worktree` with these changes: `pnpm install --frozen-lockfile`, `pnpm exec playwright install chromium`, `pnpm build`, then three shots written. |
| Every non-manual shot taken on `sample/` | `node scripts/screenshots.ts --all --out <dir>`: 17 of 17 written, exit 0; each picture looked at. `sample/` and `docs/public/` unchanged after. |
| Manual shots scriptable | No shot is `manual` any more: collision overlay (**Show collision**), new tileset (dialog with `assets/tiles.png`), new image (dialog with a name), Build panel (real build to "Build finished"), plus US-002's patched and needs-build Play shots. |
| Footer matches the project | The author chose Diamond Hands. The list's `project` is `../diamond-hands/project`, and every route names its rooms and sprites. The three patching shots set `"project": "sample"`, since Diamond Hands never reads its level data from the ROM and so can't be patched. The footer says both. All 18 were published in one `--all` run and looked at. |

## Later changes

- **Per-shot `project`, one copy and server per project.** This is for states the
  list's project can't show.
- **Everything beside the project is linked**, not only Cargo path dependencies.
  Diamond Hands includes `../../game/gfx/splash.pal`.
- **Per-shot `build`.** The script builds the copy through the studio before the
  shot, for shots that need a ROM made by this studio.
- **Found on the way, fixed in US-004.** A ROM with no data section was "needs
  build" forever, and copied folders lost the match between a build record and its
  ROM, because file times get rounded.
