# US-017 · Entity references between entities

## Approach

**Something to point at.** A placed entity has no name today: it is a type, a
position and its props, and the tools number entities by their place in the room's
list, which shifts when one before them is deleted (`entity_remove` says so). A
reference by number or by position would silently point at the wrong entity after a
delete or a move. So a placed entity gets an optional **`id`**, unique in the
project, and a reference stores that id.

- The studio gives an entity an id only when something first points at it: picking it
  as a target writes `<type>-<n>`, the smallest free `n` from 1 (`door-1`, `door-2`),
  cut to fit the 48 characters an `Id` allows. Entities nothing points at keep no id,
  so existing room files are not rewritten and new ones stay as small as now.
- Selected entity shows the id, when it has one, under the type, with how many
  entities point at it ("door-1 · 2 entities point at it"). It is not editable in
  this story (see open questions).

**The property.** `PropertyDef.type` gains `ref`, shown on the Entities page as
**Another entity**. Its default is always `""`, meaning it points at nothing: a type
cannot sensibly point every copy at one placed entity. It may have **`types`**, the
entity type ids it may point at; left out, it may point at any type. On the Entities
page the limits column of a ref is a multiple choice of the project's types.
`withPropertyType` gets the ref case (default `""`, no options, no min and max), and
changing to or from it reports the values that no longer fit through the existing
`newMisfits` dialog (US-016). A stored value fits the shape of a ref when it is `""`
or an `Id`. Whether the target exists and has an allowed type is a question across
documents, so it is a validation problem (below), not a misfit.

**Picking a target.** In Selected entity, a ref property has:

- a list: **None**, then the entities it may point at, this room's first, then each
  other room's under its name ("door-1 · Door at 120, 96", or "Door at 120, 96
  (entity 4)" for one with no id yet). The entity itself is not offered;
- a **Pick on the map** button. While picking, the markers it may point at are
  highlighted and the others dimmed and not clickable, the cursor is a crosshair, and
  a line runs from the entity to the pointer. Clicking a marker sets the reference.
  `Esc`, clicking empty ground or choosing another tool cancels. Picking works on
  markers whichever tool is on;
- the usual mark and reset button when the entity's value differs from the type's
  (US-014).

Choosing a target with no id gives it one in the same change. When the target is in
the same room that is one `commit('room', …)`. When it is in another room, the two
rooms change together in one grouped undo step (`commitGroup`, as US-015).

**The line (criterion 2).** An SVG layer over the map, under the markers, with
`pointer-events: none`, draws an arrow from each entity to each entity it points at:
from the middle of the source marker to the middle of the target's, in the source
type's colour. Lines that touch the selected entity are drawn thicker and at full
strength, the others thinner. A line follows a marker while it is dragged. For a
target in another room, the arrow runs from the entity towards where that room is on
the world map and stops at this room's edge, with the room's name at its end; clicking
the name opens that room. If either room is not on the map, the arrow is a short stub
with the name. A reference that points at nothing that exists draws no line; the
source marker gets a red dashed ring and its tooltip says why. The map's view
toggles gain **References** (on by default), beside Grid and Collision.

**What the game gets.** Codegen and the studio's section writer
(`core/src/datasection.ts`) first number every placed entity as the game does: rooms
in id order, entities in list order, which is `World::entity_index`. They then write
a reference as an **integer** property: the target's number, or -1 for none. The data
section's layout does not change, so a ROM built before this story still takes a
patched section with references in it, and `needsBuild` does not change. The
runtime gets one small reader, `Entity::reference(name) -> Option<usize>` (the
integer, `None` when negative or missing), whose result `LiveEntities::get` and
`World` already take. A host test covers it. The sample does not use references yet:
US-062 (doors and ability gates) is the first story that will.

**The rule, once.** A new `core/src/refs.ts` has the pure functions the panel, the
map, validation, the section writer and the tools share: `entityNumbers(rooms)` (id →
the game's number), `findEntity(rooms, id)`, `refTargets(docs, roomId, entity, def)`
(the list above), `freeEntityId(rooms, typeId)`, `pointAt(docs, roomId, index, prop,
target)` (the changed rooms only, giving the target an id if it needs one),
`pointersTo(rooms, id)`, `refLinks(docs, roomId)` (the lines for the map: same room,
other room with its direction, or missing) and `refProblems(docs)`.

**Problems (criterion 3).** `validate.ts` reports, in the referring room's file:

- `entity 3 (switch): opens points at "door-9", which no entity has. It was deleted,
  or its id changed: pick another target or set it to None`
- `entity 3 (switch): opens points at "sign-1", of type "sign"; it may point at type
  "door" or "gate"`
- `entity 0 (door) has id "door-1", which entity 2 of entry has too; an id names one
  entity, so change or remove one of them` (in the file of the one that comes later in
  the game's order)

and in `project.json`, starting `entity type "` so Problems opens the type (US-019):

- `entity type "switch": property "opens" may point at type "gate", which the project
  does not have`

A value of a ref that is not `""` or an id (`7`) is a misfit, reported as for any
property: `anything is 7; it is the id of an entity, or "" for none`.

Codegen reports all of these in the same words, since it cannot write a number for a
reference it cannot resolve, and so does the studio's section writer, which refuses to
patch. A fixture of bad references with the expected lines
(`codegen/fixture/bad-refs/`), read by a Rust test and a vitest test, keeps the words
from drifting apart, as `codegen/fixture/bad-behaviours` does.

**Deleting.** Deleting a target does not ask: it is one undo step, and Problems shows
at once what now points at nothing, which is what the criterion asks for. Deleting an
entity type does not clean other types' `types` lists; Problems reports the name it
left, as above.

**MCP tools.** `entity_add` and `entity_update` take an optional `id`, refuse one
another entity has (naming it), and their descriptions say that a ref property's value
is the target's id and that `entity_update` gives an entity an id. `entity_remove`
answers with the references it leaves pointing at nothing. `entity_type_set`'s
description gains `ref` and `types`. Like every write, they answer with the problems
they leave, so an agent sees a reference to a missing entity.

**Files.** `app/src/panels/room.tsx` is 938 lines. The marker (`EntityMarker`), the
reference layer and the ref field go in a new `app/src/panels/entitymap.tsx`, so
`room.tsx` gets smaller, not bigger. The story's **Touches** says core, app and
codegen. This plan also touches runtime (the reader), server (the tools) and docs.

Alternatives considered:
- *Point by room and list position, and fix references up on every delete.* Works only
  for changes the studio makes; a hand edit, an agent or a resize that cuts entities
  off silently retargets them.
- *Point by position.* Breaks on every move.
- *Give every entity an id when it is placed.* Mixed with older rooms, which have none,
  it needs the lazy rule anyway, and it fills room files with ids nothing uses.
- *An id unique per room, and `{ room, id }` as the value.* Values would no longer be a
  number, a boolean or text, which `Entity.props`, codegen's `Value` and every editor
  assume.
- *A new property tag for references in the section.* A ROM built before it would
  refuse a patched section, so adding a ref property would need a full build. An
  integer is what the game uses anyway.
- *Same-room references only.* Simpler to pick and to draw, but "a door to its
  destination" is usually in another room, and the format can hold both from the
  start.

## Format changes

Changed together: `core/src/schema.ts`, `codegen/src/model.rs`, `core/src/validate.ts`
and `docs/reference/project-format.md`.

- `Entity` gains optional `id: Id`. Unique across the project, which validation
  checks.
- `PropertyDef.type` gains `ref`. It gains optional `types: Id[]` (at least one), for
  a ref only. A ref's `default` is `""`. The refine checks all three.
- `model.rs`: `Entity` reads `id`, and `PropDef` reads `type` and `types`. US-131 will
  use `type` for its value checks.

`FORMAT_VERSION` stays 1. Old projects have neither field and load as they were. A
studio from before this story refuses a project with a ref property: its project
file does not parse there. It also drops entity ids when it saves a room. The format
page says both.

`docs/reference/data-section.md` says how a reference is written. The layout is
unchanged: an integer property holding the target's number, or -1.

## Hardware cost

- **ROM:** a ref property is one 20-byte property record on every entity of its type,
  like any own property, with no string bytes. An entity's `id` is not written to the
  ROM. The Build panel's level data readout counts it already. In the fixture, the
  section grows by 20 bytes per sign. Measured by the size of the regenerated
  `codegen/fixture/expected/studio_data.bin`.
- **IWRAM, EWRAM, VRAM:** none.
- **CPU:** none each frame. `Entity::reference` is a lookup by name like
  `Entity::int`, made when the game sets an entity up, not in the frame loop.

## Tests

- *A `ref` property type, optionally limited to some entity types:*
  - `core/test/properties.test.ts`: `PropertyDef` accepts a ref with and without
    `types`, and refuses a non-empty default, `types` on another type, and an empty
    `types`. `withPropertyType` gives a valid ref from each kind and a valid kind from
    a ref. `propertyMisfit` accepts `""` and an id, and refuses `7`, `true` and
    `"Not An Id"` in words that name the limit. `propertyAllows` gives those words.
  - `core/test/refs.test.ts` (new): `refTargets` offers only the allowed types, this
    room first, never the entity itself. `freeEntityId` skips taken ids and fits 48
    characters. `pointAt` gives a target with no id one, in the same room (one room
    changed) and in another (two rooms changed). `entityNumbers` numbers entities as
    `World::entity_index` does.
  - `cargo test` (codegen): the fixture's sign has a ref, and the generated section
    has the target's number for it, and -1 where it points at nothing. Runtime host
    test: `Entity::reference` gives `Some(n)`, and `None` for -1 and for a missing
    name.
  - `server/test/sectionwriter.test.ts`: the studio's writer gives the same bytes as
    the regenerated `studio_data.bin`, references included.
  - `server/test/behaviours.test.ts`: `entity_update` sets an id and a reference,
    refuses an id another entity has, and `entity_type_set` takes a ref with `types`.
  - Screenshot `entity-property-ref`: the Entities page with a ref property limited to
    one type.
- *The map draws a line from an entity to what it refers to:*
  - `core/test/refs.test.ts`: `refLinks` gives start and end points for a same-room
    reference (and the moved point while dragging), an edge point, a direction and a
    room name for a target in another room, a stub for a room that is not on the map,
    and a missing entry for one that points at nothing.
  - Screenshot `entity-references`: a switch with a line to its door, and an arrow to
    another room with that room's name. Plus a check, by eye, of picking on the map in
    `pnpm dev`.
- *A reference to a deleted entity is a problem:*
  - `core/test/refs.test.ts`: after its target is removed, `validate` reports an error
    in the referring room's file, in the words above. It also reports a wrong-type
    target, a repeated id, and a `types` entry naming a type that does not exist (in
    `project.json`). It reports nothing for `""` or a good reference.
  - `codegen/fixture/bad-refs/` with `expected.txt`: a Rust test (codegen's problems,
    `reports_bad_references`) and a vitest test (`server/test/refrules.test.ts`:
    `validate` and `writeSection`) both give exactly those lines.
  - `app/test/problemlink.test.ts`: the `types` problem opens the type on the Entities
    page.
  - `server/test/behaviours.test.ts`: `entity_remove` of a target answers with the
    reference it left pointing at nothing.

## Decided

Settled by the author on 2026-11-27, as recommended:

1. References to another room are included: they are picked from the list and drawn as
   an arrow to the room's edge with the room's name.
2. Ids are given by the studio and shown, not edited in the panel. Editing them, with
   the references carried, is its own story.
3. Deleting an entity that something points at does not ask. Problems reports what it
   broke, and undo brings it back.
