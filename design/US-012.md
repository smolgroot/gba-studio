# US-012 · Attach behaviours to entity types in the studio

## Approach

US-011 put behaviours in the format and checks; nothing in the studio edits them yet.
This story adds the interface and the MCP tools. No format change.

**Project settings → Entity types** (`app/src/panels/behaviours.tsx`, new; called
from `panels.tsx`, which is at 739 lines):
- Each type's row gets a chevron that opens its **behaviours** below it. The row
  also shows the behaviours' names when closed ("Patrol, Hazard").
- Each behaviour is a small card: its name, its summary, and a form generated from
  its schema in `core/src/behaviourschema.ts`. A whole number is a `NumberInput`
  limited to its range. A `true or false` property is a checkbox. A property with no
  default (`grants_ability`) is an `OptionalNumberInput` whose placeholder says it's
  required. Each field shows the default as a hint, and a value equal to the default
  is not written. A remove button and up/down buttons set the order the game runs
  them in.
- **Add behaviour** is a select of the behaviours the type doesn't have yet, each
  with its summary. A behaviour that shares a property with one the type has
  (`shooter` and `projectile`) is listed but disabled, with the reason.
- Every change is one undoable commit of `project.json`, like the rest of the
  panel. Problems (US-011a) show in the Problems panel as before.
- The text under the table changes from "What it does is written in the game's
  code" to say that it comes from its behaviours, or from the game's code.

**Room panel → Selected entity** (`room.tsx` calls `BehaviourOverrides` from the
same new file; `room.tsx` is at 916 lines, so the form doesn't go in it):
- Under the type's own properties, one subheading per behaviour of the type, with
  its fields. A field shows the type's value (or the default) as its placeholder.
- Typing a value writes it to the placed entity's `props`: an override, which US-011
  already writes, checks and plays.
- An overridden field is marked and has a **reset** button that removes the
  override. US-014 does the same for a type's own properties later; this is the
  small part behaviours need now.
- Changing an entity's type already clears its `props`, overrides included.

**MCP tools** (`server/src/tools.ts`):
- `entity_type_add_behaviour { type, behaviour, props?, before? }` adds a behaviour
  to a type, or changes the values of one it has (merging `props`). `before` puts it
  ahead of another of the type's behaviours. The description lists every behaviour
  with its properties, ranges and defaults, generated from `BEHAVIOURS`, so an agent
  doesn't have to guess.
- `entity_type_remove_behaviour { type, behaviour }`. Placed entities' overrides of
  its properties stay; the studio then warns about them as properties the type
  doesn't define. The answer says how many there are.
- Both answer with the problems they left, like every write tool.
- `entity_type_set`'s description no longer says the type's behaviour is Rust code
  matching on `EntityKind`. It points at the two new tools.

**A new enemy with no Rust change** (criterion 4). Since US-011b the sample's loop
asks every entity for patrol, collectible and hazard, whatever its type. So a new
type with a sprite and those behaviours plays with no change to `main.rs`.
`scripts/check-new-enemy.ts` proves it end to end, using only MCP tools:
1. Copy the sample into a temporary game folder, with the crates vendored as
   `pecten-studio` sets up a game.
2. Draw a 16x16 PNG into its `assets/` (a throwaway folder, not an author's).
3. `sprite_create`, `entity_type_set`, `entity_type_add_behaviour` (patrol, then
   hazard), `entity_add` in the entry room, `build`.
4. `run_rom` at two points in time. The enemy is drawn in both, at different x
   positions, and walking into it sends the hero back.

It needs the GBA toolchain and a cold build of a copy (minutes), so it's a script
run on demand, not part of `pnpm test`, as with the headless checks in earlier
stories. The pieces are in `pnpm test`.

Alternatives considered:
- *Behaviours in the Properties panel of a placed entity only.* The story says on
  types, with overrides on placed entities. Types are where an enemy is defined.
- *A JSON Schema form library* (`@rjsf/*`). It's a large dependency for two field
  kinds, and its look wouldn't match the panel's own fields.
- *An automated end-to-end test in `pnpm test`.* It would need the nightly
  toolchain and minutes of build on every test run.

## Format changes

None.

## Hardware cost

None. The interface and tools write the format US-011 defined.

## Tests

- **Criterion 1** (Project settings lists behaviours, forms from declarations):
  - `app/test/behaviours.test.ts` (vitest, as `app/test/` already has) on the pure
    helpers in the new file: the fields made for each declaration's properties
    (kind, range, required, default), what adding, removing, moving and setting a
    value do to an entity type, and which behaviours the add menu disables, with
    why.
  - A screenshot (`docs/screenshots.json`) of Project settings with the sentry
    bot's behaviours open, taken by `scripts/screenshots.ts`.
- **Criterion 2** (placed entities show and override):
  - Helper tests: which value a field shows (override, type value, default), what
    an override and a reset write.
  - A screenshot of the room panel with a sentry bot selected.
- **Criterion 3** (MCP tools): `server/test/behaviours.test.ts`. Adding, changing,
  ordering with `before` and removing write the right `project.json`. Unknown
  types and behaviours get errors in the project's terms. The answers carry the
  problems left (an out-of-range value).
- **Criterion 4** (a new patrolling enemy from a PNG, no Rust change, plays):
  `scripts/check-new-enemy.ts`, run on demand, as above. Its pictures and output
  are recorded in this note.

## Decisions

- Reset for overrides, and criterion 4 as a script: both accepted by the author (2026-11-22).

## Built as

- **The editing helpers are in `core`** (`core/src/behaviours.ts`), since both the
  studio and the MCP tools use them: `withBehaviour`, `withoutBehaviour`,
  `moveBehaviour`, `setBehaviourValue`, `behaviourBlocker`, `behaviourFields`,
  `behaviourLabel`, `shownBehaviourValue` and `behaviourOverride`. They're tested in
  `core/test/behaviouredit.test.ts` (9 tests), which were written first and failed
  first. That's not `app/test/` as planned, because nothing in them depends on the
  app.
- **The interface** is in `app/src/panels/behaviours.tsx` (`TypeBehaviours`,
  `BehaviourOverrides`), with two small additions to `fields.tsx`: disabled options
  in `SelectInput`, and a marked label on `Field`.
- **The MCP tools** are in `server/src/behaviourtools.ts`, tested in
  `server/test/behaviours.test.ts` (5 new tests, failing first).
- **Screenshots:** `entity-behaviours` and `entity-overrides` in
  `docs/screenshots.json`. The second selects the sentry bot with a new script
  action, `clickAt`, which clicks at a point of the page, and overrides
  `patrol_pace`.
- **Criterion 4:** `node scripts/check-new-enemy.ts` passed on 2026-11-22. The
  tools all answered "No problems", the build took 81 s, and the copy's `src/` was
  identical to the sample's. In game pixels:
  - the crawler's x at the four pictures: 69.75, 61.75, 49.75, 32.25;
  - the hero's x: 24.75 at the start, 10.75 after walking left, then 22.75, sent
    back to where it entered the room after the crawler walked into it.
