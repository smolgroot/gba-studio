# US-016 · Edit entity property definitions in the interface

## Approach

**Project settings → Entity types.** The row of a type already opens to show its
behaviours. It opens to a **Properties** table above them, in a new
`app/src/panels/properties.tsx` (`panels.tsx` is about 740 lines; behaviours have their
own file already). A row per property: name, type, default, what limits it (an enum's
options, an int's smallest and largest), and a bin. **Add property** adds an int named
`property` (`property-2`… as `property_2`), default 0. Every edit of one field is one
`commit('project', …)`, so one undo step, as for entity types and collision classes.

The default and the limits follow the type, and every commit keeps the definition valid,
because a definition the schema refuses makes the whole project file fail to load:

| Type | Default | Limits | Changing to it |
| --- | --- | --- | --- |
| int | a whole number | optional smallest and largest | default 0 (kept if it fits) |
| bool | yes / no | none | default no |
| string | text, may be empty | none | default empty |
| enum | one of the options | the options, at least one | options: the old text default if there is one, else `option`; default the first |

The options are one text field, separated by commas (blank and repeated ones dropped).
Taking out the option that is the default makes the first option the default.

**What stands on a property.** A placed entity stores a value under the property's name
(only when it differs from the type's: US-014). So:

- **Rename.** The stored key is renamed in every room's entities of that type, in one
  grouped undo step with the project (`commitGroup`, as US-015). The editor refuses a
  name that is not snake_case (`^[a-z][a-z0-9_]*$`), is another of the type's
  properties, or is a property of one of the type's behaviours (what the build refuses).
- **Delete.** A property nothing stores is deleted at once. One that entities store is
  asked about first: a dialog lists the rooms and entities, and says their values go.
- **Change of type, of the options, or of the limits.** `core/src/properties.ts` works
  out which stored values no longer fit the new definition (`propertyMisfits`). If there
  are none the change is made. If there are, a dialog lists them (room, entity number
  and type, the stored value, why it does not fit) and offers **Change and drop them**:
  the unfit values are dropped, so those entities follow the property's new default, in
  one grouped step with the project. **Cancel** leaves the definition as it was. This is
  the report the story asks for. A renamed option is a removed option plus a new one; it
  does not carry values across.

**The rule, once.** `core/src/properties.ts` (new) has the pure functions the interface,
the validation and the MCP tool share: `propertyFits(def, value)` and
`propertyMisfit(def, value)` (the reason, in the author's words: "is 7; it is true or
false", "is “loud”; it is one of calm, angry", "is 12; it is a whole number from 0 to 9"),
`propertyMisfits(docs, typeId, next?)`, `withPropertyType`, `propertyNameProblem`,
`newProperty`, `renameProperty`, `withoutProperty`, `dropMisfits`. Changes that reach
rooms return `{ project, rooms }` with only the rooms that changed, as `ClassChange`.

**Validation.** `validate.ts` (where it already warns about a name the type does not
define) now also reports a stored value that does not fit its definition, as an error in
the room's file: `entity 3 (sentry): mood is "loud"; it is one of calm, angry`. So a hand
edit, an agent's edit, or a type changed elsewhere shows in Problems, not only in the
dialog.

**The range.** The story says "range", and `PropertyDef` has none. This note adds
optional `min` and `max` to an int property (additive; whole numbers within 32 bits,
`min <= default <= max`, int only). The room panel's number field for it takes them, so
a value outside is not typed in the first place. Without them an int is any 32 bit
whole number, as now.

**The MCP tool.** `entity_type_set` replaces a type's properties as a whole, so it
cannot tell a rename from a remove and an add. It now says, in its answer, which placed
entities hold values the new definitions do not fit (the same `propertyMisfits`, by
name), as `entity_type_remove_behaviour` already says what it leaves behind. It does not
change the rooms: an agent edits them with `entity_update`.

**The notice** that a refused undo leaves (US-015) moves from the collision table to
the top of Project settings, so it shows once, whichever table the change was in.

Alternatives considered:
- *No range, only enum options.* Smaller, but the story names it and a number field with
  limits is how a designer stops a bad value at the source.
- *Refuse a change that breaks stored values.* Leaves the author hunting by hand; the
  dialog lists them and drops them with one undo.
- *Convert values across a retype (7 to “7”, 0 to false).* Guesses at what the author
  meant, and an int 2 for a bool has no right answer. The default is the safe answer.
- *Check the stored values in codegen too.* The build then fails on a bad value as it
  does for behaviours. It needs `type`, `options` and the limits in `model.rs` and the
  same words in Rust and TypeScript, which is its own story (below).

## Format changes

`PropertyDef` gains optional `min` and `max` (int only). Changed together:
`core/src/schema.ts` (fields, and the refine that checks them with the default),
`codegen/src/model.rs` (`PropDef` reads them; codegen does not use them yet),
`core/src/validate.ts` (the stored-value check) and `docs/reference/project-format.md`.
`FORMAT_VERSION` stays 1: old projects have neither field and load as they were. An
older studio drops them when it saves, which the docs say.

## Hardware cost

None to the ROM's layout: a property is the same 20 byte record per entity as now, with
a limit that is not stored. Each own property costs 20 bytes on every entity of its type
(and text, for strings) in the level data section, which the Build panel's level data
readout already counts; the docs say so where properties are described.

## Tests

- *Every property type in the schema can be defined from the interface:*
  - `core/test/properties.test.ts`: `withPropertyType` gives a valid definition for each
    of int, bool, string, enum from each of the others (parses with `PropertyDef`, default
    fits, options only on enum, limits only on int); an enum keeps at least one option and
    its default among them; `newProperty` has a free valid name; `propertyNameProblem`
    refuses invalid, repeated and behaviour-clashing names.
  - `core/test/core.test.ts` (or `properties.test.ts`): `PropertyDef` accepts int `min`
    and `max` and refuses them on other types, `min > max`, and a default outside.
  - The `entity-properties` screenshot: a type open with one property of each type.
- *Changing a property's type reports the placed entities whose values no longer fit:*
  - `core/test/properties.test.ts`: `propertyMisfits` lists room, entity, value and
    reason for int→bool, bool→enum, an enum option removed, a narrowed range, and nothing
    for an entity that stores no value or one that still fits; `dropMisfits` and
    `renameProperty` change only the rooms that need it and keep the others' identity.
  - `core/test/core.test.ts`: `validate` reports a stored value that does not fit as an
    error in the room's file, in those words, and nothing for a value that fits.
  - `app/test/store-group.test.ts`: a change of type with dropped values is one undo step
    across the project and the rooms, undone and redone together.
  - `server/test/behaviours.test.ts` (or a new file): `entity_type_set` answers with the
    entities the new definitions break.
  - The `entity-property-misfit` screenshot: the dialog listing them.
- *No data-section change:* `core/test/prefab.test.ts` still shows a retyped property's
  default reaching entities that store nothing, and a section written before and after a
  rename (with the rooms carried) is equal apart from the name.

## Decided

- The range is int `min` and `max` on `PropertyDef`, as above.
- A change that breaks stored values asks, lists them, and drops them on confirm, with a
  grouped undo; Problems reports any that remain.
- Codegen does not check own properties' values yet: US-131 is added for it.
- `editProperty` in `core/src/properties.ts` works out a change from the documents it is
  given, and the dialog's confirm calls it again with the documents as they are then, so a
  question left open never writes stale documents. After a Cancel or a refused field the
  rows are made again from the project, so a field never shows text the project did not take.
- Adding a behaviour is refused (and says why) when the type has its own property of the
  same name as one of the behaviour's, as the property is refused the other way round.
