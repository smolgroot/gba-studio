# US-006 · Data reserve and section use in Project settings

## Approach

**Project settings.** The Build section gains a "Level data reserve" field, in
bytes. It is empty when `build.dataReserve` is left out, with the placeholder
"Default: a quarter of the data, at least 4 KiB". Clearing it removes the key from
`project.json`, so the build goes back to the default. What is typed is read by a
small pure function, `parseReserve` in `app/src/datause.ts`. It takes whole bytes
from 0 to 1 MiB, the schema's range, and refuses anything else, so the old value
stays. A new `OptionalNumberInput` in `app/src/fields.tsx` holds the draft text,
the way `NumberInput` does, but lets it be empty. One commit is one undo step, as
for the other fields.

**Section use.** `Builder.status()` already stats each ROM. It now also reads the
ROM's data section header (`readSection` from core) and adds
`data: { used, capacity } | null` to `RomInfo`. It is null when the ROM has no
section. The result is cached by path, size and modification time, so the status
checks that run on every file change do not read the ROM again. The header's
`used` and `capacity` are what the build or the last patch wrote, so the numbers
follow patches too: `rom-patched` and `build-finished` already carry a fresh
status.

**Build panel.** Under the buttons, one line per built ROM, from
`dataUseLine(mode, info)` in `app/src/datause.ts`: "dev ROM · level data 9,812 of
14,036 bytes (70%), 4,224 free". It is in the warning colour above 90%, where a
small edit may need a full build. A ROM with no section says that its game does
not read level data from the ROM.

Alternatives considered:
- A separate `/api/rom-data` endpoint: one more fetch for something the build
  status already carries.
- Taking the numbers from the build log: they would be lost on reload and would
  not follow patches.

## Format changes

None. `build.dataReserve` already exists in `core/src/schema.ts`,
`codegen/src/model.rs` and `docs/reference/project-format.md` (US-001).
`FORMAT_VERSION` is unchanged.

## Hardware cost

None. The change is studio-only. The server reads the ROM once each time it is
rebuilt or patched.

## Tests

- Project settings field: `app/test/datause.test.ts`. `parseReserve` gives
  `undefined` for an empty field, keeps 0 and in-range values, and refuses
  negative, fractional, too-large and non-numeric input. The field itself is
  checked in the running studio (screenshot).
- Build panel use: `server/test/buildstatus.test.ts`. `Builder.status()` reports
  `used` and `capacity` from a ROM's section header, `null` for a ROM without
  one, and new numbers after the file changes. When the sample ROM is built, it
  also checks the sample's own numbers. `app/test/datause.test.ts` checks the
  line's wording and its warning threshold.
