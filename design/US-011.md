# US-011 · Behaviours declare their properties to codegen

## Approach

Today a behaviour finds its settings by looking up property names on the entity
(`entity.int("patrol")`). Nothing checks those names, and the lookup is the whole of
US-010a's extra frame time. This story makes behaviours something an entity type
*has*, with properties the runtime declares, the studio and the build check, and the
game reads by position.

**1. Declarations, written once, in the runtime.** Each behaviour gets a
`DECLARATION` const next to its code:

```rust
pub const DECLARATION: Declaration = Declaration {
    id: "patrol",
    number: 0,
    summary: "Walks back and forth around where it was placed.",
    props: &[
        PropDecl::int("patrol", "Pixels each way", Some(32), -32768, 32767),
        PropDecl::int("patrol_pace", "Frames to walk a pixel", Some(2), 1, 255),
    ],
};
```

`behaviour::DECLARATIONS` lists all ten. `number` is the behaviour's stable id in the
ROM. Numbers are only ever added, never reused. A prop with no default is required.
The types are `int` (with a range) and `bool`, which is all the ten need.

- **Codegen** depends on the runtime already (for the data writer), so it reads
  `DECLARATIONS` directly.
- **The studio** reads `core/src/behaviourschema.ts`: one JSON Schema per behaviour,
  plus its id, number and summary. Codegen writes that file from `DECLARATIONS`
  (`cargo run -p pecten_studio_build --bin behaviours-schema`), and a codegen test
  fails if the committed file is out of date. This is the same pattern as the
  shared fixtures. The CLI `pecten-studio schema` includes it. There's no MCP tool for schemas: agents read the format from the tool descriptions and the docs.

**2. The project format: an entity type lists its behaviours.**

```json
{ "id": "sentry-bot", "sprite": "sentry-bot", "props": [],
  "behaviours": [ { "id": "patrol", "props": { "patrol": 32 } }, { "id": "hazard" } ] }
```

- `props` in a behaviour entry are the type's values. Anything left out takes the
  declaration's default.
- A placed entity overrides one with the same flat `props` map it already has (for
  example `"patrol": 48`). Behaviour property names are unique across behaviours
  (the US-010 naming rule), so there's no ambiguity.
- The studio's interface for this is US-012. Until then it's edited in
  `project.json` or through the MCP document tools.

**3. Problems, in the studio and in the build alike** (`core/src/validate.ts` and
codegen, with a shared fixture of bad projects and the messages expected):

- An unknown behaviour ("entity type "sentry-bot" has behaviour "patroll"; the
  behaviours are patrol, collectible, …"). The same behaviour listed twice.
- A property its behaviour doesn't declare, a value of the wrong type, or a value
  out of range ("patrol_pace is 0; it runs from 1 to 255"). This applies on the
  type and on placed entities.
- A required property with no value on the type or on a placed entity of that type
  (`grants_ability`).
- A type's own property with the same name as one of its behaviours' properties
  ("rename one").

**4. The ROM: properties by position.**

- **Entity properties:** codegen and the TypeScript writer (live apply) write each
  entity's properties as the type's own first, then each behaviour's, in the
  declaration's order. So within an entity type, a behaviour's properties start at
  a fixed position.
- **A new table:** a ninth section, `S_BEHAVIOURS`, holds per entity type
  `{ first u16, count u16 }` into a list of `{ number u16, first property u16 }`.
- **Compatibility:** the table of sections is built to grow (readers skip sections
  they don't know), so the section stays at version 1. A section with 8 entries
  reads as "no behaviours".
- **Reading:** `Entity::behaviour(number) -> Option<Settings>` finds the entry
  (comparing a few u16s, no strings), and `Settings::int(i)` / `bool(i)` read
  property `i` of the declaration.

**5. Behaviours read only what they have.** `Behaviour` gets `const DECLARATION`.
Every `from_entity` becomes `entity.behaviour(Self::DECLARATION.number)` followed by
reads by position.

- `from_entity` now answers "does this entity's type have the behaviour", not "does
  it have a property with this name". So `Hazard::from_entity` and
  `Checkpoint::from_entity` stop accepting every entity.
- `Entity::int(name)` stays for a game's own properties.

**6. The sample moves over.**

- **Its project:** the sentry bot gets `patrol` and `hazard`, and coins and diamonds
  get `collectible`. Their own `patrol` and `value` properties go.
- **Its code:** the loop asks each entity for `Patrol`, `Collectible` and `Hazard`
  and no longer checks the type. `scripts/make-sample-project.ts` writes the new
  project.

Alternatives considered:
- *A `behaviours.json` in the runtime crate as the source.* The runtime would need
  a JSON parser or a build script to know its own property positions. Rust
  declarations that codegen reads need neither.
- *Per-type tables compiled into the game's code instead of a section.* Adding a
  behaviour to a type would then need a full build. In the section, live apply can
  do it.
- *Keep name lookups, but cache them per type in RAM.* That adds per-game RAM and a
  warm-up, and the build still couldn't check anything.

## Format changes

- **`project.json`:** `entityTypes[].behaviours`, optional, `[]` by default. Old
  projects load unchanged, so `FORMAT_VERSION` stays at 1. Changes go together in
  `core/src/schema.ts`, `codegen/src/model.rs`, validation and
  `docs/reference/project-format.md`.
- **Data section:** a ninth section, `S_BEHAVIOURS`, in `runtime/src/data/layout.rs`,
  `write.rs` and `core/src/datasection.ts`. Behaviour properties come after the
  type's own in entity records. Documented in `docs/reference/data-section.md`. Same
  version.
- **A breaking change for games:** an entity whose type doesn't list a behaviour no
  longer gets it from a property name. This only affects code written since US-010,
  which is the sample's.

## Hardware cost

- **ROM:** 4 bytes per entity type plus 4 per behaviour attached. The sample's
  entity properties stay the same size: its `patrol` and `value` move from the
  type's own properties to its behaviours'.
- **RAM:** none.
- **CPU:** `from_entity` becomes a lookup by entity type plus a scan of 1 to 4
  entries, then reads at fixed positions. Measured with `--features measure` on the
  US-010 run. The goal is the US-011 criterion: an average of 296 or less. It was
  289 with no lookups at all.

## Tests

- **Criterion 1** (declared once, exported as JSON Schema):
  - A runtime test checks that every behaviour's `from_entity` reads the positions
    its `DECLARATION` lists.
  - A codegen test checks that `core/src/behaviourschema.ts` matches `DECLARATIONS`.
  - A vitest test checks that every schema in it is valid JSON Schema and that the
    studio's validation uses it.
- **Criterion 2** (problems, not surprises):
  - A fixture project `codegen/fixture/bad-behaviours/`, with one of each problem.
  - Codegen's test and `core/test/validate.test.ts` both check for the same list.
  - A server test checks that the MCP write tools answer with them.
- **Criterion 3** (no name lookups in the frame loop, frame time):
  - A runtime test reads settings by position from a world whose properties are in
    a scrambled order.
  - The shared fixture `codegen/fixture/expected/studio_data.bin` is regenerated
    with behaviours and checked byte for byte by both writers.
  - Measured: `--features measure`, the same run as US-010, with an average of 296
    or less.
  - The sample's headless pictures stay identical to US-010's baseline.

## Decisions

- **Split** (author, 2026-11-21):
  - **US-011a:** declarations, JSON Schema, the `behaviours` field and the
    problems. Codegen and the TypeScript writer already write behaviour properties
    after the type's own, still with their names, so a behaviour attached in
    `project.json` works with the name lookups `from_entity` still does.
  - **US-011b:** the `S_BEHAVIOURS` table, reads by position, and moving the sample
    over.
- **Required properties** (author): `grants_ability` has no default. Every other
  property has one.
- **Clean break** (author): in US-011b, `from_entity` gives a behaviour only to
  entities whose type lists it. There's no fallback to name lookups.

## Built as, US-011a

- **The schema file is a TypeScript module**, `core/src/behaviourschema.ts`, not a
  `.json` file. `core` imports no JSON anywhere, and doing so would need
  `resolveJsonModule` and import attributes under Node. The module is one exported
  constant holding the JSON. Codegen writes it
  (`cargo run -p pecten_studio_build --bin behaviours-schema`), and
  `the_studio_has_the_behaviour_declarations` fails when it differs. The CLI
  `pecten-studio schema` includes it under `behaviours`.
- **Each entry has an `order` list**, the property names in declared order, because a
  JSON object's keys have none (`serde_json` sorts them). The TypeScript writer uses
  it.
- **Problems.** `codegen/fixture/bad-behaviours` has one of each problem.
  `reports_bad_behaviour_settings` (codegen) and
  `server/test/behaviourrules.test.ts` (the studio) both check that they report
  exactly the lines of its `expected.txt`. The studio test sits in `server/test/`
  because `core` has no Node types to read files with.
- **Writing values.** The main fixture's `sign` type has `checkpoint` and `door`,
  with `needs_ability` 4, overridden to 7 on one sign. `studio_data.bin` was
  regenerated, and both writers give it byte for byte. The runtime still reads by
  name in US-011a. Writing the names keeps that working.
- **Shared property names.** `shot_speed` is declared by both `projectile` and
  `shooter`, and a type can't have both. A type with two behaviours that share a
  property is a problem.

## Built as, US-011b

- **The section.** Section 8, `S_BEHAVIOURS`, is in halfwords: the number of entity
  types, then per type `{ first, count }`, then `{ number, first property }`
  entries. A section with 8 sections reads as having no behaviours
  (`a_section_from_before_behaviours_reads_with_none`). Both writers give the
  regenerated fixture byte for byte.
- **Reading.** `World::new` splits the section into its two tables once. Each
  `Entity` finds its type's entries when it's read. `Entity::behaviour(number)` and
  `Entity::behaviours()` scan only those entries, and `Settings::int(i)` reads by
  position. Behaviours implement `from_settings`; `from_entity` is a default built
  on it. Nothing reads a property by name
  (`settings_are_read_by_position_not_by_name`).
- **The sample.** Its types list their behaviours. The loop asks every entity for
  `Patrol`, `Collectible` and `Hazard` and checks no types. The headless pictures
  are identical to the US-010 baseline.

**Frame time** (release, `--features measure`, the US-010 run; hundreds of cycles,
worst and average):

| Build | Worst | Average |
| --- | --- | --- |
| Before US-010a | 709 | 296 |
| US-010a: by name, given by type | 721 | 312 |
| Position reads, entries looked up on every call | 725 | 318 |
| The same, but patrol and hazard only for sentries | 718 | 305 |
| Tables split once, entries found per entity | 717 | 304 |
| The same, each entity's behaviours walked once | 720 | 306 |
| The same, without the type tag check | 720 | 308 |
| **Kept: tables split once, `from_entity` per behaviour** | **716** | **301** |
| Settings hardcoded in the sample, no ROM reads | 704 | 289 |

The rest of the cost is reading each entity's behaviours and settings from ROM
every frame. Neither the number of lookups nor the way they're made changes it
much, so small changes won't reach 296. Settings have to be read once and kept,
which is US-013's live entity table, or a cache in the sample.

**Decision** (author, 2026-11-21): the frame-time target moves to US-013, as a new
criterion there. US-011b closes at 301.
