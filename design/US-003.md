# US-003 · Live-apply edits to the running game

## Approach

Patch on change (US-002) rewrites the ROM file and the Play panel restarts the
game from it. Live apply keeps the running game and changes it in place:

1. The server patches the ROM file as now. The Play panel fetches the new ROM,
   as it does to restart.
2. If live apply is on, the panel compares it with the ROM that is running. When
   only the data section differs, the ROM has a debug record with an inbox
   (below), and the running game reads it, the panel:
   - writes the changed bytes of the section into the emulator's copy of the
     cartridge (`patch_rom`, new in the Pecten core),
   - moves the game's collected bits to the entities' new numbers, clearing the
     bits of entities that changed or are new (`read_ram` and `write_ram`, new),
   - writes to the game's **inbox** what changed: tiles, physics, entities, or
     rooms and the map.
3. Each frame the game polls the inbox (`debug::Live::poll`). On a change it
   reads the world again. On a physics change it takes the new settings. On a
   tile or room change it redraws the view at the camera. The player's body, the
   camera, the clock and the score are the game's own, so they stay as they are.
4. Otherwise (live apply off, a release ROM, code changed, or a game that does
   not poll), the panel restarts as before. A game that has not taken a change
   within 30 frames is restarted with the new ROM, so nothing is left stale.

**Why the studio moves the collected bits.** Entities are numbered across the
project, room by room. Adding a coin to the first room moves every later number,
so the game's collected bits would end up on the wrong entities. The studio
compares the old and new entity lists room by room. An entity that is the same
(type, position and properties) keeps its bit under its new number. One that
changed or is new starts uncollected, which respawns it. Nothing else in the
sample has entity state: patrols follow the clock. A live entity table (US-013,
US-021) will need the same matching.

**Why a fresh `World` on every change.** A patch can move the section's tables
(longer strings, more entities), so a `World` made before it points at the wrong
places. `World` is `Copy` and cheap to make. `WorldView` now keeps its own copy
instead of a reference. The game can then replace both, and `view.set_world`
swaps the world without redrawing when no tiles changed.

**Pecten core** (`../gba-wasm`): `WasmEmulator` gains `read_ram(addr, len)`,
`write_ram(addr, bytes)` (EWRAM and IWRAM only), and `patch_rom(offset, bytes)`.
These are thin wrappers over `GbaCore` methods, tested in Rust. They clear the
idle-loop detector as `load_state` does, because the memory a parked loop waits
on may have changed. The studio's copy in `app/public/wasm/` is rebuilt with
`scripts/sync-pecten.sh`. The core's save states hash the whole ROM, so a state
saved before a live patch does not load after it. Rewind (US-023) will have to
save one after each patch.

**Debug record v2.** The record gains the inbox's address and size (28 bytes).
Inbox: `generation`, `changed` (bits: 1 tiles, 2 physics, 4 entities, 8 rooms
and map), `seen`. The studio ORs bits into `changed` and adds one to
`generation`. The game, polling, copies `generation` to `seen` and clears
`changed`. Both writes happen between frames, so they cannot interleave. The
studio still reads v1 records (no inbox: live apply restarts instead).

**Toggle.** A **Live apply** checkbox in the Play panel, on by default, under
**Patch on change**. Off, a patch restarts the game as before.

Alternatives considered:
- *Restart and load a save state.* The state's ROM hash refuses a patched ROM,
  and the game would keep values it had already read, such as physics.
- *Game watches the section's bytes for changes.* Hashing 14 KB a frame costs far
  too much CPU, and the game still could not renumber the collected bits.
- *The game remaps entities itself.* It would need the old section, which the
  patch has replaced.

## Format changes

None to the project format. Debug record and map version 2: the inbox fields are
added, and `docs/reference/debug-map.md` is updated. The block layout is
unchanged.

## Hardware cost

- EWRAM: 12 bytes for the inbox. ROM: 8 more bytes of record and the polling code.
  Nothing in release builds.
- CPU: one volatile load and a compare a frame. On a change, `World::new` (checks
  the section) and, for tiles, a redraw of the tile layers in view
  (`WorldView::redraw`, which keeps the pictures behind). Measured on the sample:
  the game skips two updates while it redraws (`server/test/liveapply.test.ts`
  compares it with a game that took no change). Redrawing only the changed cells
  is US-007.

## Tests

- *Painted tiles appear within a few frames and the player keeps their position
  and state:* `server/test/liveapply.test.ts` runs the sample's dev ROM headless.
  After walking right, a front-layer tile in view is changed and applied live.
  Within 5 frames the screen differs where the tile is and nowhere else, and the
  player's body (position, speed, on ground) is unchanged by the apply.
- *Physics changes take effect on the next frame:* same file. The run speed is
  raised and applied while the hero walks; the next frame's speed is the new one.
- *Entity edits respawn only the entities that changed:* `server/test/liveapply.test.ts`
  takes two coins, moves one in the studio, and applies live. The moved coin is
  uncollected and the other stays collected. Also, adding an entity to an earlier
  room keeps the collected bits on the right entities. The matching is tested
  alone in `server/test/liveapply.test.ts` too, on section bytes.
- *A toggle turns live apply off; restart-on-change still works without it:*
  the Play panel's **Live apply** checkbox (`app/src/panels/play.tsx`). Off, the
  panel takes the restart path it has today. Checked by hand in the studio, and
  by the fallback test: a ROM without an inbox gives `restart`, never a partial
  apply.
- Pecten core: Rust tests for `read_ram`, `write_ram` and `patch_rom`, including
  addresses out of range.
- Runtime: host tests for `Live::poll` (sees a change once, writes `seen`, clears
  `changed`) and for the record v2 layout against the fixture.

## Open questions

- The studio writes between video frames. A game whose frame runs past the next
  vertical blank could be mid-update then, and read a half-changed world through
  its old `World` until it polls. The sample finishes well within its frame, but a
  heavy game might not. A fix would have the game publish "waiting for the next
  frame" and the studio wait for it.
- Releasing the Pecten core change: it is left uncommitted in `../gba-wasm`, with
  the studio's copy rebuilt from it.
