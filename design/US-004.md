# US-004 · Say when a change needs a full build

## Approach

The studio works out, for a built ROM, whether it matches the project. It answers
with one of these states:

| State | Top bar | Meaning |
| --- | --- | --- |
| `up-to-date` | Up to date | The ROM is what a build would give now. |
| `patched` | Patched | Up to date, because level data was patched in since the build. |
| `needs-build` | Needs build: *reason* | Only a build can bring it up to date. |
| `can-patch` | Level data changed · **Patch** | Only level data changed, and it has not been patched in yet (Play is not running, or **Patch on change** is off). |
| `building` | Building… | A build is running. |
| `none` | Not built | There is no ROM yet. |

The story names the first three. The last three can happen too, and leaving them
out would mean showing something untrue. The top bar shows the dev ROM, which is
the one Play starts by default, or the release ROM if there is only that one.

**What US-002 already detects.** Before patching, the ROM's manifest is compared
with the project: entity types and their sprites, collision classes, rooms,
tilesets and their tile counts, pictures and tracks. It also says when the data no
longer fits. That stays, and gives the data-side reasons.

**What it misses, and how this story catches it: a record of the build's inputs.**
Codegen also compiles some things into code that the manifest does not hold. These
are sprite documents (anchor, hitbox, animations), `audio.json` (formats,
soundfonts, sound effects) and the pixels of every PNG and sound file. The game's
Rust code is compiled too. The studio can't read these back out of a ROM, so it
records them when it builds.

- *Inputs* are the crate files (`Cargo.toml`, `Cargo.lock`, `build.rs`,
  `rust-toolchain.toml`, `src/**`, `.cargo/**`), `studio/sprites/*.json`,
  `studio/audio.json`, and every asset the documents name: tileset images, sprite
  sheets and palette files, room backgrounds, tracks, soundfonts and sound effects.
- When a build **starts**, the server hashes the inputs (SHA-1, cached by size and
  modification time). Taking the hashes at the start means an edit made during
  the build still counts as a change. When the build ends with exit 0, it writes
  `<rom>.build.json` beside the ROM. The file holds the hashes, the ROM's
  modification time and `patched: false`.
- After a patch, the server rewrites that file with the ROM's new modification
  time and `patched: true`.
- A status check hashes the inputs again and compares. Reasons are in the
  project's terms: `Rust source changed: src/main.rs`, `new sprite "bat"`,
  `sprite "coin" changed`, `assets/hero.png changed`, `the audio list changed`.
  There are at most three file names, then "and N more".

**ROMs built outside the studio** (`cargo build` in a terminal) have no record, or
one whose modification time is not the ROM's. For those, an input whose file is
newer than the ROM counts as changed ("src/main.rs changed after the ROM was
built"). This is coarser, but it never says "up to date" after a later edit.

**Patching refuses too.** `patchRom` checks the inputs first, so a patch no longer
says "up to date" when only a PNG or `src/` changed. That was the gap US-002 left.
Status and patch share one check, so they can't disagree.

**Where it shows:**
- Server: `GET /api/rom-status[?mode=]` returns the state. The page fetches it
  again on every file change, build message and patch.
- Top bar, and the desktop app's tab strip: one short label. Hovering shows the
  reasons, and a needs-build or can-patch state has a button (**Build** or
  **Patch**).
- Play panel: it already shows the patch's needs-build line; that stays.
- MCP: `run_rom` adds a line when the ROM it runs is out of date, so an agent
  doesn't judge a stale game.

Alternatives considered:
- *Only modification times, no record.* A patch rewrites the ROM and moves its
  time past every edit, so a code change before the patch would be lost.
- *Hashes in the ROM's manifest, written by codegen.* Codegen doesn't see the Rust
  source, and the manifest would need a new layout for each new kind of input.
- *Watch events only (dirty flag in memory).* This is lost when the server
  restarts, and doesn't cover builds or edits made while the studio is closed.

## Format changes

None in the project format. A new build output, `<rom>.build.json`, is written next
to the ROM. It is not part of the project, is in the ignored `dist/` in the sample
and scaffold, and is documented in `docs/guide/build-and-play.md`.

## Hardware cost

None: nothing changes in the ROM or the runtime. On the host, a status check reads
and hashes about 30 files for the sample (about 200 KB). After the first check,
unchanged files are skipped by size and modification time.

## Tests

| Criterion | Test | Where |
| --- | --- | --- |
| Top bar shows up to date / patched / needs build with reason | `romStatus` returns `up-to-date` after a build record, `patched` after a patch, `can-patch` after a data edit, `needs-build` with the reason after a compiled-side edit; the top bar renders the label from that state (checked in the browser) | `server/test/freshness.test.ts`, `app/src/App.tsx` |
| A `.rs` file sets needs build | `a Rust source change needs a build`: edit `src/main.rs` after the record; also new and removed `.rs` files, and the mtime fallback without a record | `server/test/freshness.test.ts` |
| A sprite sheet sets needs build | `a sprite sheet change needs a build`: change a PNG's bytes, add a sprite document, change a sprite's animation | `server/test/freshness.test.ts` |
| Patch refuses with the same reasons | `patchRom` answers `needs-build` with the Rust reason, leaves the ROM alone | `server/test/freshness.test.ts` |
| Build writes the record from the start | a fake build command that edits a source file while it runs leaves the ROM `needs-build` | `server/test/freshness.test.ts` |

## Open questions

- A sprite document's display `name` is not compiled, but changing it still counts
  as a change, because whole files are hashed. Hashing only the compiled fields
  would avoid that, at the cost of a list to keep in step with codegen.
- Changes to the studio's own `runtime/` and `codegen/` crates (path dependencies
  in a checkout) are not tracked. Only contributors make them.
