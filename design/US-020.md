# US-020 · Symbol map of game state

## Approach

Today the runtime keeps no game state of its own. The sample keeps its state in
locals of `main`: the hero's `Body`, the camera, the room and the collected bits.
The linker places those on the stack, so a debug map has nothing fixed to point at.
This story gives that state one fixed home and a way to find it.

**A state block in RAM (runtime, new `debug` module).** `debug::GameState` is a
`#[repr(C)]` record of 32-bit words: a stamp (`PSGS`), the frame count, the room
index, the camera, the player's `Body`, and the address and length of the
collected bits. `debug::publish(&GameState)` copies it with volatile writes into one
`static` that agb's linker places in EWRAM. The game calls `publish` once a frame,
after it has moved everything. The stamp lets a reader tell a published block from
a game that has not published yet (all zeros).

**A record in ROM that points at it.** A second `static`, `PECTDBUG` followed by a
version, the block's address and its size, sits in `.rodata`. The linker fills in
the address. `publish` reads the address back from this record with a volatile
read. The record is then referenced, so `--gc-sections` keeps it, and the copy
always lands where the record says.

**The build writes the map.** After a studio build succeeds (`Builder`, used by the
Build panel, `pecten-studio build` and the MCP `build` tool), the server scans the
ROM for `PECTDBUG` and writes `<rom>.debug.json` beside it. The map holds the
block's address and layout, the player body's layout, the collected bits, and the
data section's address, which the server finds by scanning for `PECTDATA` (US-001).
Only the section's address goes in the map, not its sizes, because a patch changes
those and the map would go stale. Its header has them.
The layouts are fixed per record version, in `core/src/debugmap.ts`. A shared
fixture keeps that file and the Rust layout the same.

**Release builds leave it out.** The static, the record and the copy are compiled
only with `debug_assertions`, which dev builds have and release builds do not, or
with the runtime's `debug-map` feature, which forces them on. Without either,
`publish` is an empty inline function, so the ROM has no record. The build then
writes no map and removes a stale one.

**Name.** The story says `debug.json` next to the ROM. The sample keeps both ROMs in
`dist/`, so one shared name would let a release build delete the dev ROM's map. The
file is `<rom>.debug.json`, the same pattern as `<rom>.build.json` (US-004).

**Entity table.** No live entity table exists yet: entities are read from the data
section, and the sample works out where a sentry is from the clock. The map covers
what exists now: the entity records in the data section (by its address and the
documented layout in `docs/reference/data-section.md`), the collected bits, and the
frame count that patrols follow. A live entity table in RAM comes with generated
dispatch (US-013). The record's version then goes up and the map gains it.

Alternatives considered:
- *Read symbol addresses from the ELF.* Needs the ELF, whose path is the author's
  build command's business, and an ELF parser in the server. A record in the ROM
  works from the `.gba` alone.
- *A fixed address picked by the runtime.* agb's allocator owns EWRAM, so any
  address could collide with it.
- *Layouts described inside the ROM.* More ROM and code for no gain while one
  runtime version writes one layout. The record's version says which layout applies.
- *Codegen writes the map.* Codegen runs before linking, so it cannot know the
  addresses.

## Format changes

None to the project format. New: the `PECTDBUG` record (version 1) and
`<rom>.debug.json` (version 1), both documented in `docs/reference/debug-map.md`.
`physics::Body` becomes `#[repr(C)]`, so its layout is fixed. No change to its API.

## Hardware cost

- ROM: 20 bytes for the record, plus the copy in `publish` (a few dozen bytes of
  Thumb code). Nothing in release.
- EWRAM: 64 bytes for the block (16 words). Nothing in release.
- IWRAM, VRAM: none.
- CPU: 16 volatile word stores and one load per frame, under 100 cycles of the
  frame's 280,896.

## Tests

- *Each build writes `<rom>.debug.json` with addresses and layouts:*
  - `runtime/src/debug.rs`: the field offsets and size match
    `codegen/fixture/debug-layout.json`, `publish` writes the block with the
    stamp, and the record points at the block.
  - `server/test/debugrecord.test.ts`: `DEBUG_LAYOUTS` equals the same fixture;
    a record is read; a ROM with no record gives none; a wrong version, size or
    address gives a problem in plain words; a block is read by its layout. (Core
    tests have no Node types to read the fixture, so these sit with the server's.)
  - `server/test/debugmap.test.ts`: a successful build writes the map beside the
    dev ROM and says so in the log, and a failed build leaves an old map alone.
    The sample's dev ROM is then run headless and its EWRAM read from a save
    state at the mapped address. The stamp, the start room and the hero's start
    position are there, the collected bits point into RAM, and after 60 frames of
    Right the frame count is up by 60 and the hero has moved right.
- *Release builds can leave it out:*
  - `server/test/debugmap.test.ts`: a ROM without a record (as a release build
    makes) gets no map, an old one is removed, and the dev ROM's map is not
    touched.
  - A real `pecten-studio build sample --release`: no `PECTDBUG` in
    `dist/sample.gba`, and no map. With `--features pecten_studio_rt/debug-map`,
    the release ELF has the record.

## Open questions

- A live entity table: see **Entity table** above. Deferred to US-013 and US-021.
- Reading memory: the Pecten core has no memory read call, so the real-ROM check
  reads EWRAM out of a save state. US-021 will want a proper call in the core.
