# US-021 · Live entity inspector in the Play panel

Split in two, one branch each:

- **US-021a** · the list of the player and the live entities, updated every frame,
  and selecting one by clicking it on the game screen. Read-only.
- **US-021b** · editing a number, written to memory, used by the game on the next
  frame. Planned when US-021a is done; its open questions are under the story.

The rest of this note is US-021a.

## Approach

US-020 left two things to this story: a live entity table a tool can read, and a
call in the Pecten core to read memory. The second is done: the core has `read_ram`,
`write_ram` and `patch_rom`, which live apply uses. The first is not. US-013 added
the table (`LiveEntities<N>`, a static made by the generated `data::entities()`),
but nothing says where it is, and its layout is Rust's to choose.

**A fixed layout for the table (runtime).** `LiveEntities` keeps
`[Option<LiveEntity>; N]`. Rust packs the `None` into a spare value of some field,
and which one is not fixed. The slots become `[LiveEntity; N]`, and `LiveEntity`
gets a private `built` flag. It sits in the two bytes of padding after `index`, so a
slot stays 108 bytes. A separate `Slot { built, entity }` record would have cost 4
bytes a slot. `Actor`, `Hitbox` and `LiveEntity` become `#[repr(C)]`. Field order
puts what a tool reads first: the actor (position, speed, facing, alive, hitbox),
then `kind`, `room`, `index`, `built`. The behaviours come last and are not
described to tools. Their enum has no fixed layout, and the list
can show properties from the data section instead (below). The API is
unchanged apart from two things. `get`, `active` and the rest still give
`&LiveEntity`, and `slots_address` and `LiveEntity::BUILT_AT` are new for the
debug module. `LiveEntity` can no longer be built with a struct literal outside the
runtime, which nothing did. `Actor::home` is a
tuple, whose inside is not fixed either, so it is left out of the published layout.
Only its size counts towards the offsets after it, and the layout test pins those.

**Where the table is (runtime, codegen).** The record gets a fourth part: the
address of a small cell, `EntityTable { address, slots, slot_size }`, all words.
The generated `data::entities()` calls `debug::show_entities(&TABLE)` once, when it
hands the table out, and that call fills the cell. Every game that uses the
generated table gets the inspector with no change to its own code, and it costs
nothing per frame. The record version goes to 4 and the record to 52 bytes. The new
part is appended after the start override, so the offsets of versions 1 to 3 stay
where they are. The state block does not change (64 bytes).

**Reading it (core).** `core/src/debugmap.ts` gains layout version 4, the field
types `i16` and `u16`: the cell's
fields and the slot's fields (`x`, `y`, `vx`, `vy`, `facesLeft`, `alive`,
`hitbox.{x,y,w,h}`, `kind`, `room`, `index`, `built`), checked against
`codegen/fixture/debug-layout.json` as today. `DebugMap` gets `entities: { address,
size, fields, slot: { size, fields } } | null`. A new `core/src/inspect.ts` has one
pure function, `readLive(emulator, map, section)`. From a frame's RAM and the running
ROM's data section it gives the player (from the block) and then the built, alive
entities of the active rooms. For each entity it gives the type id (from the
section's manifest, by `kind`), the room id, the position, speed, facing and
hitbox, and the entity's properties as placed. The properties are read from the
running ROM's data section (`readPlacements` in `datasection.ts`, which keeps
the section's byte layout in one file), so they are what the game was given, even
after a live apply. Positions are world pixels, speeds as the game holds them: the player's in
1/256 pixel a frame, an actor's in whole pixels a frame. The list says which.

**Which entities are live.** `LiveEntities` keeps its active ranges private. The
list shows every built, alive slot of the active rooms: those whose `room` is the
block's room or a room touching it. The studio works out which rooms touch from the
section's room table, as `enter` does. That way the cell needs no copy of the
active ranges. Alternative: publish the active ranges too (16 more words per frame).
That is not needed while "touching" is the same rule in both places. A test runs
both on the same rooms.

**The panel (app).** An **Entities** list beside the game screen in `PlayView`
(`app/src/panels/inspector.tsx`), shown while the **Entities** box is ticked. It
sits under the screen when the panel is narrow. After the frames due in an
animation frame, `readLive` runs once and the list draws from its result, so React
sees one update a frame and only the last of a catch-up. The selected entity's box
is outlined on the screen, so a pick can be seen. The player is first. Each entity shows its type,
room, position and speed, and opens to show its hitbox and properties. A dev ROM
from before version 4 shows the player only, with "Build again to see entities: this
ROM was built by an older studio." A release ROM shows "Release builds have no debug
map: play the dev ROM to inspect."

**Clicking the game screen (app, core).** The canvas is drawn 240×160 and scaled to
fit. A click becomes a game pixel, then a world pixel by adding the camera from the
block. `pickAt(live, x, y)` in `inspect.ts` returns the entity whose hitbox holds the
point (the actor's feet plus the hitbox offset), or the player's body. Where boxes
overlap it returns the smallest, so a coin in front of a door can still be picked.
The list selects it and scrolls to it. A click on nothing clears the selection. The
selected entity's row stays selected by its world index while it lives. If it is
collected or its room stops being active, the row says so and stays until another
pick.

Alternatives considered:
- *The game copies its entities into the block each frame.* Up to `LIVE_ENTITIES`
  slots a frame of CPU and EWRAM, and US-021b's writes would land in a copy.
- *Keep `Option` and work out its layout from a test build.* Rust may change it
  between compilers; a fixed layout is cheap.
- *The game calls `shown.entities(entities)`, as it does for the collected bits.*
  Every game and the starter crate would need the call. The generated code can make
  it instead.
- *Read the ELF's symbols for `TABLE`.* As in US-020: the ELF is not the studio's.

## Format changes

None to the project format. `PECTDBUG` record version 4 (52 bytes, entity table cell
appended) and `<rom>.debug.json` version 4 with an `entities` part, documented in
`docs/reference/debug-map.md`. The studio still reads versions 1 to 3; they have no
entity table. `Actor`, `Hitbox` and `LiveEntity` become `#[repr(C)]` with no change
to their API. `LiveEntities` stores `Slot`s inside; its API is unchanged.

## Hardware cost

- ROM: 8 bytes more for the record, and a few dozen for `show_entities`. Nothing in
  release.
- EWRAM: 12 bytes for the cell. Slots unchanged at 108 bytes, measured by
  `a_live_entity_is_small` and pinned by the layout fixture: `built` is in what was
  padding. Nothing for the cell in release.
- IWRAM, VRAM: none.
- CPU: none per frame. `show_entities` runs once.
- Studio: one `read_ram` of `slots × slot_size` bytes a frame (about 7 KB for 64
  slots), in a frame budget the emulator already spends far more of.

## Tests

As built. Tests that need a file from `codegen/fixture/` sit with the server's, as
in US-020, because core's tests have no Node types.

- *A panel lists live entities, updated every frame, with the player first:*
  - `runtime/src/debug.rs`: the layout (block, body, inbox, start, cell, slot)
    matches `codegen/fixture/debug-layout.json`. `show_entities` fills the cell with
    the table's address, slot count and slot size. The record points at the cell.
  - `runtime/src/behaviour/live_tests.rs`:
    `a_tool_reads_the_table_at_the_published_offsets`: slots read as raw bytes give
    the same position, speed, alive, hitbox, kind, room, index and `built` as `get`,
    and a cleared table has every `built` at 0. `a_live_entity_is_small` measures the
    slot (108 bytes). `active_rooms_match_the_shared_fixture` checks
    `codegen/fixture/active-rooms.txt`.
  - `codegen/src/lib.rs` `generates_the_fixture_project`: the generated `entities()`
    calls `debug::show_entities`.
  - `server/test/debugrecord.test.ts`: `DEBUG_LAYOUTS[4]` equals the fixture. A v4
    record is read, with its entity part. A v3 record still reads, with
    `entities: null`. A wrong cell size, or a cell outside RAM, gives a problem in
    plain words.
  - `server/test/inspect.test.ts`: `indexSection` reads the codegen fixture's rooms,
    types and properties (UTF-8 text included). `readLive` on a fake emulator gives
    the player first, then only built, alive entities of the active rooms, and
    follows a change from one frame to the next. It waits for a block with no stamp,
    says why only the player is listed for a v3 ROM or a game without the table, and
    gives a problem for a bad slot size or a table outside RAM. `activeRooms`
    matches the same `active-rooms.txt` as the runtime.
  - `server/test/debugmap.test.ts`: the sample's dev ROM, run headless. After 120
    frames `readLive` lists the player first, then every entity of `entry` and the
    touching `shaft` but the player start, with coins and diamonds where they were
    placed. After 60 frames of Right the frame is up by 60, the player has moved
    right and the sentry has moved.
  - In the app: the `play-entities` screenshot (`docs/screenshots.json`) plays the
    sample and shows the list following the game.
- *Clicking one on the game screen selects it in the list:*
  - `core/test/inspect.test.ts`: `pickAt` maps a screen point to a world point with
    the camera, returns the entity under it, the smallest of two overlapping, the
    player, an entity with no hitbox by a small box on its feet, or nothing (which
    clears the selection).
  - In the app: the `play-entities` screenshot clicks coin #1 on the canvas and
    waits for its row to open ("Properties as placed"), with the coin outlined on
    the screen.

## Open questions

- Properties per behaviour: the behaviours hold their own copies of their settings,
  which a patrol may change as it runs (its phase, for example). The list shows the
  settings as placed, from the data section, not those copies. Showing a behaviour's
  running state needs a layout for each behaviour; that can be a later story if
  authors want it.
- Entities made while the game runs (projectiles from a pool, spawner children) are
  not in the table. They are listed when the pool gets a cell of its own: a new
  story if needed.
