# US-005 · Play from the room and spot under the cursor

## Approach

The game reads where to start from the ROM's debug record, which only dev builds have
(US-003 added the record's inbox the same way). The record gains a **start override**:
four words in ROM, `set`, `room`, `x`, `y`, all zero as built. The studio never
writes it to disk. To play from a spot, the Play panel loads the ROM into the emulator
and then writes the four words into the emulator's copy of the cartridge
(`patch_rom`, from US-003). The game's `start()` calls `debug::start_override()`, which
returns `Some` only when `set` is 1 and the room exists; otherwise the game starts as
before.

- **Release builds ignore it** because they have no record: `start_override()` is
  `None` without `debug_assertions` or the `debug-map` feature, and the studio finds
  no record to patch, so it says "this ROM has no debug record; build dev".
- **Spot** is a room and a point in room pixels in the form entities use (middle of
  the tile's bottom edge, `entityAt`), so the player stands on that tile. The game
  places the body with `Body::standing_at`, as for the `player-start` entity.
- **Room panel**: a new tool, "Play from here" (key `P`). Right button already
  erases, so a click with this tool is the gesture. It stores the spot in the studio
  store (`playFrom`) and opens the Play panel, which starts the game there.
- **Play panel**: the spot stays for restarts caused by rebuilds, so tuning a late
  room keeps you in it. The Play and Reset buttons clear it and start from the start
  room. The panel says "Started in room X at (x, y)" while it is set.
- Room index is the room's position among the sorted room ids, as the data section
  numbers them (`sortedIds`). Rooms added after the ROM was built make the patch
  refuse by the existing live-apply rules, so the index is always the ROM's.

Alternatives considered:
- *Write the spot into EWRAM.* The game has already started by the first poll, so it
  would need a restart handshake; the ROM word is read at boot with no timing.
- *Patch the ROM file.* Leaves a debug-only start in an artefact the author keeps.
- *Right-click menu.* Right button is erase; a tool is consistent with the rest.

## Format changes

No project format change (`schema.ts`, `model.rs`, validation unchanged). The **debug
record** goes to version 3: 44 bytes, the start override at offset 28. Version 2
records still read (no override: the studio says to rebuild). `DEBUG_LAYOUTS[3]`,
`codegen/fixture/debug-layout.json` and `docs/reference/debug-map.md` change together,
and `.debug.json` gets a `startOverride` entry (ROM address, size, fields).

## Hardware cost

Debug builds only: 16 bytes of ROM in the record and a few dozen for the read, once at
boot. Release: none. No RAM, no per-frame cost.

## Tests

- Game starts at the point: `debug::start_override` host test in `runtime/src/debug.rs`
  (set, unset, room out of range); `core` test that the patch bytes for a room and tile
  are the expected words at the map's address; headless `run_rom` of the sample with the
  override patched shows the player in the chosen room (check, with pictures).
- "Play from here" in the map editor: vitest on the pure helper that builds the
  spot and the patch (`core/src/startpoint.ts`); the tool and the Play panel wiring
  are checked in the running studio.
- Debug-only: debug layout fixture test (record v3) and a `debugmap` test that a ROM
  without a record gives no override target; the runtime function is `None` when
  built without the debug map.

## Open questions

- Should the Play panel keep the spot across a manual "Restart"? Proposed: no, only
  across rebuilds.
