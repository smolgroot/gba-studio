# US-030 · Palette and tile budgets while painting

## Approach
Today only the build helper knows how many tiles and palettes an image needs
(`codegen/src/image.rs`: `tileset` packs each tile's colours into the palette that
needs the fewest added, `background` then keeps one of each tile). The studio only
gets those numbers back from a built ROM's manifest (`core/src/datasection.ts`). So:

- **One TypeScript copy of the packing, in `core/src/budget.ts`** (pure, no DOM, no PNG
  decoder; it takes RGBA pixels):
  - `tilesetCost(rgba, width, height)` → `{ tiles, palettes }`, or a failure in the
    build helper's words: size not a multiple of 8, `tile N uses C colours`, `tile N
    needs a 17th palette`. The greedy packing is copied step by step, ties included,
    because a different packing gives a different palette count.
  - `backgroundCost(...)` → the same plus `distinct`: tiles that are the same pixels
    *and* the same palette count once, as in `image::background`.
  - `roomBudget(docs, roomId, costs)` → what one room puts on screen, counted the way
    codegen does: palettes = the tileset's own + each distinct background picture's;
    tiles = the distinct tiles of **every room drawn with the same tileset** + each
    picture's distinct tiles; layers = the most tile layers of those rooms +
    backgrounds. A room with no backgrounds is shown against the tileset's own count,
    as codegen checks it.
  - `budgetProblems(docs, costs)` → errors with the same wording as codegen
    (`lib.rs` lines 240 and 448–482), on `studio/tilesets/<id>.json` and
    `studio/rooms/<id>.json`.
- **Problems.** `validateProject` takes an optional `art` lookup (asset path →
  cost). The server decodes the tileset and background PNGs with `pngjs` (already a
  server dependency) and keeps each result until the file's mtime changes, so a
  reload stays fast. When `art` is left out (as `patch.ts` does today), nothing
  changes. The Problems panel already opens the document a problem is on, so a
  problem on the tileset or room opens that item.
- **Readouts in the app** (`app/src/panels/budget.tsx`). They sit at the right end of
  the editor's toolbar, in a slot of their own (`Viewport`'s `status`), so they are never
  cut short. They read "312/1024 tiles · 9/16 palettes", amber from 90%, red over, with a
  tooltip saying what counts. The server sends each image's cost with the project
  (`Bundle.art`, by `artKey`), so the app loads no PNGs for this. What is being painted
  is counted in the browser:
  - *Tileset editor*: the tileset's cost, or "not convertible" with the build's message.
  - *Pixel editor*: `imageBudget` on the in-memory pixels at the end of each stroke. It
    gives the image's cost, and the fullest room that uses it. A sprite sheet gets no
    readout, because sprite memory is US-031.
  - *Room editor*: `roomBudget` on the store's documents, which hold each stroke as
    soon as it ends.
- **Shared fixture** `codegen/fixture/budget.json`: small images written as pixel
  grids (a list of colours and rows of one character per pixel, `.` transparent),
  with the expected `tiles`, `palettes`, `distinct` or error for each. The cases are
  palette reuse, a tie between palettes, a new palette, exactly 16, a 17th, 16
  colours in one tile, a repeated tile under two palettes, and a size that is not a
  multiple of 8, plus colours the GBA cannot tell apart and half-transparent pixels. A
  Rust test in `codegen` runs `image::tileset`/`image::background` on it; a vitest in
  `server/test` runs `budget.ts` on it (the server tests have Node types to read files,
  as with `dim.json`). Both must equal the JSON. The images are pixel grids, so no PNG
  decoder is needed.
- **Room totals match codegen too**: the fixture project in `codegen/fixture/studio`
  is checked both ways. `generate` now returns `Report::budgets` (one `RoomBudget` per
  room), which a Rust test compares with the `project` block of `budget.json`. A
  vitest in the server loads the same project and runs `roomBudget` against that block.

Alternatives, one line each:
- Ask the server for costs over HTTP after each save. Too slow for "within a second"
  while painting in the pixel editor, and it adds a round trip per stroke.
- Compile the Rust packing to WASM for the app. One source of truth, but it adds a
  wasm toolchain to the app build for about 60 lines of logic. The shared fixture
  keeps the two in step instead.
- Use only the numbers from the last build. They are stale exactly when the author
  needs them.

## Format changes
None. No schema fields, `codegen/src/model.rs` untouched, `FORMAT_VERSION` stays.
`validateProject` gains an optional parameter; callers that do not pass it behave as
now.

## Hardware cost
None in the game: this is studio-side counting only. The ROM is unchanged, and the
data section and codegen output stay byte for byte the same (the existing
`generates_the_fixture_project` test and `expected/studio_data.bin` check this).
Studio cost: packing a 256×256 image (1024 tiles × 16 palettes) is about 1 ms in
the browser. Estimated; to be measured in a vitest on a 1024-tile image.

## Tests
1. *Readout updates within a second, in tileset, pixel and room editors*:
   `server/test/budget.test.ts` counts a 1024-tile, 16-palette image in under 100 ms.
   `core/test/budget.test.ts` checks that a room's readout follows a stroke, and that
   `imageBudget` counts unsaved pixels. In the built studio, painting a filled rectangle
   in the pixel editor moved the readout from 17/16 to 2/16 palettes 15 ms after the
   stroke, while the file was still "Unsaved" (a Playwright run on a scratch copy of the
   sample). The retaken screenshots show the three readouts.
2. *Matches the build helper (shared fixtures)*: `codegen/fixture/budget.json`, read by
   `image::tests::counts_the_shared_budget_fixture` and
   `tests::room_budgets_match_the_shared_fixture` in Rust, and by
   `server/test/budget.test.ts` (the images, and the fixture project's rooms through
   `pngjs`).
3. *Over turns red and adds a problem on the item*: `core/test/budget.test.ts` checks
   the errors over 16 palettes, over 1024 tiles, for an image that cannot be converted
   and for a tileset over 1024 tiles, with their files and the build's wording.
   `server/test/budget.test.ts` loads a project whose background goes over, sees the
   problem, then sees it go once the picture is fixed. `budgetState` is tested for
   amber and red. `pecten-studio validate` on a scratch copy of the sample reports the
   error on `studio/rooms/entry.json`. A screenshot of that copy showed "17/16 palettes"
   in red in the room and pixel editors.

## Open questions
Settled with the author: amber only near a limit, with no warning in Problems. A
problem that appears after the auto-save and reload is close enough. Sprite budgets
are left to US-031.
