# US-022 · Debug overlays on the game screen

## Approach

Four overlays, each drawn by the studio over the picture the emulator made, from
what the studio already reads: the live view (`readLive`, US-021a) and the running
ROM's level data section. The game and the runtime do not change.

| Overlay | Shows | Read from |
| --- | --- | --- |
| **Hitboxes** | The box of the player and of each live entity; a small cross on the feet of an entity whose type has no hitbox | the live view's rows (`rowBox`) |
| **Collision** | Each cell the physics treats as not empty, by its class's kind: solid filled, one-way a thin line along the top, slope as its floor, hazard hatched, custom outlined | the section's collision cells and classes |
| **Camera** | A cross at the middle of the view, where the camera looks, so how far the player is from it can be seen; the camera's world position is written under the screen | the live view |
| **Rooms** | The border of each room on the map that is on screen, the player's room brighter; the world's 240x160 screen grid in a faint line | the section's rooms |

**Pure drawing in core (`core/src/overlays.ts`).** Two functions, no emulator in
either:

- `overlayShapes(view, section, on)` → a list of shapes (`rect`, outlined or filled,
  and `cross`) in **game pixels of the screen** (world minus camera, clipped to
  240x160), for the overlays in `on`. Each shape carries the overlay it belongs to.
- `drawShapes(pixels, shapes)` paints them into the 240x160 RGBA buffer `step_frame`
  returned, one game pixel per pixel, before it is put on the canvas. "At the game's
  scale" is then true by construction: the canvas scales the picture, and the
  overlay with it, so a hitbox edge is one game pixel wide at any zoom.

The panel keeps one flag a overlay (a row of check boxes beside **Entities**: Hitboxes,
Collision, Camera, Rooms), reads the live view when the list or any overlay is on
(today only when the list is), and draws before `putImageData`. The existing outline
of the selected entity stays as it is.

**Collision cells from the running ROM.** `indexSection` gains `cells` (per room: its
columns and rows, and the one byte of collision class a cell has) and `classes` (each
class's kind and slope heights), read from the section the game was given, so they
are what the physics sees even after a live apply. A room is 1 byte a cell; the
sample's whole world is a few KB, read once per ROM, as the rest of the index is.

**Camera, and why there is no target.** The console has no camera: it has scroll
registers, and "the camera" is the world pixel a game puts at the screen's top-left,
which the debug block holds. How a game aims it (follow the player, ease, stop at the
map's holes) is the game's own code, so the studio does not guess a target. The
overlay shows only what is true of every game: the middle of the view, and the
camera's position.

Alternatives considered:
- *Draw on a second canvas laid over the first.* It would not be at game scale unless
  sized to match, and it gives a second thing to keep aligned. Painting into the frame
  buffer cannot be out of place.
- *Read collision from the studio's project documents.* Simpler, but it is not what
  the game has when a change is waiting for a build, and it needs the tileset art to
  know each tile's class. The ROM's cells are exactly what the physics reads.
- *The ROM draws its own overlays.* Costs the game ROM, VRAM and frame time, and
  needs a build to turn on. Ruled out by the second criterion.

## Format changes

None. No change to `schema.ts`, `model.rs`, validation or `FORMAT_VERSION`. The debug
record and the data section are read as they are.

## Hardware cost

None on the console: nothing under `runtime/`, `codegen/` or `sample/` changes. In
the studio: at most 31 x 21 cells,
the boxes of the live entities and a few lines a frame, painted into a buffer already
in hand, about 2,000 shapes at the very most; measured in a test run against the
sample (see Tests).

## Tests

- *Each overlay has its own toggle:*
  - `core/test/overlays.test.ts`: with one overlay on, `overlayShapes` gives only
    its shapes, for each of the four; with none, none. With all on, the shapes are
    the four sets together.
  - The `play-overlays` screenshot (`docs/screenshots.json`) ticks each box in turn.
- *…and draws at the game's scale:*
  - `core/test/overlays.test.ts`: a hitbox, a cell, a room corner and the camera
    cross land at the screen pixel that is their world pixel minus the camera, at
    camera positions at and between whole screens, and shapes past the edge are
    clipped, not wrapped. `drawShapes` writes exactly one pixel wide lines into a
    240x160 buffer and nothing outside it.
  - `server/test/overlays.test.ts`: the sample's dev ROM run headless; the pixel at
    the player's top-left on screen is the overlay's colour in the buffer
    `drawShapes` painted, and the pixel beside it is the game's.
- *Overlays are drawn by the studio, not the ROM, so they cost the game nothing:*
  - `server/test/overlays.test.ts`: two emulators run the sample's dev ROM on the
    same buttons for 300 frames. One is read and painted every frame with all four
    overlays on; the other is not. Their frames before painting, the game's state
    block, the entity table and the ROM bytes are equal at the end. The reading
    emulator is wrapped so a `write_ram` or `patch_rom` call fails the test.
  - `git diff --stat` for the story shows no change to the game's code
    (`runtime/src` outside the test, `codegen/src`, `sample/src`); noted in the
    summary.

## Decided

- **The camera has no target.** It is the middle of the view only: a game's camera
  rule is its own code, and the debug block holds only where the camera is now. A
  target can be its own story if projects get a camera setting.
- **Overlays do not need the Entities list open.** They read the live view
  themselves.
