# US-001 · Fixed-layout data section in the ROM

## Approach

Codegen stops writing level data as Rust values (`ROOMS`, `CLASSES`, `PHYSICS` and
`WORLD` in `studio_data.rs`). It writes one binary file, `studio_data.bin`, and the
generated code brings it in as a single 4-byte-aligned `static` byte array. The
runtime reads rooms, classes, entities, properties, world placement and physics
straight from those bytes through small view types. Nothing is copied into RAM and
nothing is allocated.

**What goes in the section:** rooms (id, name, size, world placement, music,
tileset index, tile layers, background layers with their parallax), collision cells,
entities, entity properties, collision classes, the start room and physics.

**What stays compiled:** tileset pixels and palettes, background picture pixels,
sprites, animations and audio. These go through agb's converters and macros. The
section refers to them only by index (`tileset 0`, `background 2`, `track 1`). Tile
*layers* are maps, not graphics, so they are in the section. Without them, US-002
could not patch a painted room, which is the most common edit. (Agreed with the
author.)

**One layout, shared:** the byte layout is defined once, in
`runtime/src/data/layout.rs`. The reader is `runtime/src/data.rs`. The writer,
`runtime/src/data/write.rs`, is behind the `write` feature, which codegen turns on.
So the build and the game cannot disagree, and the runtime's tests build their
worlds with the same writer. When the studio copies the crates into a game's
`vendor/`, it points the build helper at the copied runtime.

**Finding the section:** it starts with an 8-byte magic number, `PECTDATA`, on a
4-byte boundary. A tool scans the ROM for the magic number and reads the header,
which gives the version, the bytes in use, the capacity and a table of offsets. A
custom linker section was considered, but agb's linker script would have to be
changed and kept in step with agb. Scanning for the magic number needs nothing from
the linker.

**Stopping the compiler from baking values in:** the generated `data::world()`
reads the slice with `core::ptr::read_volatile`, so no value of the section can be
folded into the code. A ROM test patches the jump speed in the built sample and
checks that the game jumps differently.

**Reading as fast as fields:** each table is viewed as fixed-size word arrays (for
example rooms are `&[[u32; 16]]`), after `World::new` has checked that the section
is 4-aligned. A field is then one aligned load at a constant index, with no bounds
check. Two other reads were made cheaper so the sample plays at the old cost or
better:
- Finding a cell's room compares tile coordinates, with no division. The GBA
  divides in software, and physics asks for every cell it tests.
- The view remembers the room the last tile it streamed came from.

**Runtime API (breaking, in `pecten_studio_rt::data`):**

- `World<'a>`: `World::new(bytes, &Limits) -> Result<World, DataError>` checks the
  magic number, the version, every table, record and string, and that every
  tileset, picture, track and entity type is one the game was built with. After
  that, the getters do not fail.
- `world.room(i)`, `world.rooms()`, `world.collision_class(i)`, `world.class_id(i)`,
  `world.physics()`, `world.start()`, `world.entity_count()`,
  `world.room_at_tile(col, row)` (new). Unchanged in meaning: `camera_target`,
  `cross`, `room_at`, `room_at_screen`, `origin`, `entity_index`, `enclosed`.
- `Room<'a>`: `id()`, `name()`, `cols()`, `rows()`, `world()`, `music()`, `tileset()`,
  `collision()`, `class_index()`, `layer_count()`, `layer(n)`, `tile(n, col, row)`,
  `backgrounds()`, `entity(i)`, `entities()`, `first_entity()`.
- `Entity<'a>`: `kind`, `x`, `y` fields as before; `prop`/`int`/`bool`/`str`.
- `Cells::class` returns `CollisionClass` by value. The class no longer holds its
  id: that is `world.class_id(i)`.
- `gfx`: `RoomGfx` and `BackgroundLayer` are gone. `WorldView::new(&world, gfx::ART, room, &mut graphics)`;
  `RoomView::new(room, &gfx::ART, &mut graphics)`; `Background` lives in `data`.

**Generated code:** `include_data!` gives `data::world()`, `LIMITS`, `ENTITY_COUNT`,
`EntityKind`, `class::*` and `room::*`. `include_gfx!` gives `ART` and no longer
`ROOMS`.

Alternatives considered:
- *Decode into fixed-capacity arrays in EWRAM at boot.* This costs RAM and a second
  copy of the data, and the capacity would have to be compiled in anyway.
- *`#[repr(C)]` structs cast over the bytes.* The ROM layout would then follow
  Rust's struct layout. The word-array view gives the same speed with one small
  cast.
- *Keep tile layers compiled.* Smaller now, but US-002 could then patch only
  entities and physics.

## Layout (version 1)

Documented byte for byte in `docs/reference/data-section.md`, and defined in
`runtime/src/data/layout.rs`.

- A 20-byte header (`PECTDATA`, version, section count, used, capacity), then a
  table of 7 `{ offset, length }` pairs.
- Strings, classes (12 bytes each), rooms (64), entities (12), props (20), cells,
  and globals (92: start room, entity count, 21 physics numbers).
- Background parallax is `u16`, because 100% is 256, which does not fit in a byte.
- Zeros follow up to the capacity.

## Format changes

- `core/src/schema.ts` and `codegen/src/model.rs`: optional `build.dataReserve` in
  `project.json`, in bytes, 0 to 1 MiB, validated by the schema. Left out, the
  reserve is a quarter of the data, rounded up to 1 KiB, and at least 4 KiB.
- No `FORMAT_VERSION` bump. The field is optional and old projects load unchanged.
- The section has its own layout version (1), separate from `FORMAT_VERSION`.
- `docs/reference/project-format.md` has the new field. The new page
  `docs/reference/data-section.md` has the layout.

## Hardware cost

Measured on the sample's dev build (opt-level 3), on the Pecten core. The same
33-step button script was run before and after: walk, jump, ramp, coins, sentry
knock-back, into the second room.

- **ROM:** 291,292 → 307,184 bytes (+15.9 KB). The section uses 10,468 bytes. Of
  those, 9,600 are collision and layer cells, which were in the ROM before too; the
  rest is records and strings (791 bytes) and the header. A 4,096-byte reserve
  follows, for a capacity of 14,564. The rest of the growth is the reading code,
  inlined where it is used, and the checks.
- **IWRAM, EWRAM, VRAM:** no change. `World` is 8 slices on the stack, and nothing
  is copied.
- **CPU per frame** (timers 2 and 3 chained, `--features measure`):

  | | Before | After |
  | --- | --- | --- |
  | Worst frame | 168,900 cycles | 165,400 cycles (−2%) |
  | Average frame | 43,400 cycles | 40,800 cycles (−6%) |
  | Full view load | 2,027,710 cycles | 2,014,730 cycles (−0.6%) |
  | Physics, per frame | 11,060 | 6,780 |
  | Tile streaming, per frame | 10,570 | 11,730 |
  | Entities, per frame | 8,580 | 8,940 |

  The first game frame appears on the same video frame as before, and all 33
  screens are identical pixel for pixel.

## Open questions

- `Collected` stays sized by the compiled `ENTITY_COUNT`. A patched ROM with more
  entities cannot remember the extra ones. US-002 should report that as needing a
  full build. (Agreed with the author.)
- Tile streaming is still about 11% above the old code per frame, more than made up
  for by the physics. It can come down further if a later story needs the time.
